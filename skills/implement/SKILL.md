# Implement

收到 `Brief` 走「执行一片」。收到 Spec、MMF、普通计划或单独的完整需求走「整体验收」。小改动以用户的请求为 spec。字段和 JSON 调用方式见[交接合同](../to-tickets/references/delivery-contract.md)。

## 执行一片

1. 核对当前工作树起点与 `base`，读取 `read_first` 和项目约定。复述本片的场景、`goal`、`expected` 和排除项。缺先例、范围或业务决定时，带原票号、片标识和缺口回交技术负责人。
2. 调用 `bdd` 选择可证明本片结果的公开入口。已有检查能拒绝对应错误时直接复用。缺陷在同一输入和入口先复现再修复。需要新检查时，写明它能拒绝哪一种既有证据拒绝不了的错误。仅修改 `writable` 所列文件和目录内的文件，运行合同的 `check` 和明确归本片的风险检查。范围不足时记录缺口。
3. 按授权提交获准文件。在干净的交付提交上实际运行 `check`，从输出读回约定结果，对照独立预期。将实际命令、SHA、观察值和成功与否写入 `record.run`，将未完成项写入 `record.gaps`。在目标仓库根向 `node <本 Skill>/scripts/implement.js` 输入 `{input: brief, record}`，把输出的 `SliceEvidence` 交回技术负责人并结束本片。没有提交时保留缺口。全量门禁和双轴审查由 MMF 负责人集中执行。

## 整体验收

直接实施时从第 1 步开始，已收回所有执行片时从原 Spec 和开工前 SHA 恢复验收清单，集成后进入第 3 步。从派发时的完整合同清单逐片收回执，包括尚未交回的片。另按 Spec 的场景清单逐项收集成观察。一个场景可以验收多片共同实现的结果。

上下文吃紧时，已有用户委派授权可将大块读取交给子代理，按 `principle-guard-the-context-window` 收摘要。需要交接时，列出任务分支、当前 SHA、改动、已验证项、缺口和恢复后的第一个动作。用户已授权 WIP 提交时按 `git-worktree` 第 3、4 节把恢复说明写入提交正文；缺提交授权时直接交回恢复说明。

## 1. 读入验收

开始时记下当前提交的 SHA，作为第 5 步审查的 fixed point。

用户给了票号时，从 issue tracker 读取并先说出票标题；票号有歧义就问。

从 spec 逐条拆验收：每个“必须”和“不得”都有一条。每条验收要带独立预期：输入或动作、期望结果、来源（判断依据见 `bdd`）。spec 或计划里缺的，从原文补；指不出来源的，停下来问用户。编排派发（packet 带 Lane ID）时不问用户：把缺来源的验收写进工件，以 `LANE_DONE <lane> BLOCKED needs-decision:acceptance-source; <工件路径>` 结束。

spec 用代码写了 Interface 时，每条 `Ensures:` 也是一条验收，实现的签名与它一致。需要偏离时，把偏离和理由写进交付说明。

按改动命中的情况，再列失败方式，它们也是验收：

- **异步写**：等待期间换身份或离开、迟到响应、取消、重入。
- **持久写**：部分失败、重启恢复、旧版本数据。
- **状态跨步骤，或有重试、取消、不可逆副作用**：对照 spec 的 Business Flow 状态图；没有就画一张，放进交付说明，让用户判断是否符合意图。

逐个核准从原场景的 Seam 执行、能断言全部结果的命令。取得观察前，将命令、场景编号、Seam、完整 T/R 和原 `then` 写入 `MmfPlan.scenarioChecks`，保留这份批准记录供最终核收。

完成条件：fixed point 的 SHA 已记下；spec 的每个“必须”和“不得”都有验收；每条验收都有独立预期，或已经交给用户确认；命中的失败方式已列出。

## 2. 按切片实现

动手前先做减法：按运行时目录完整读取 `principle-subtract-before-you-add/SKILL.md` 和 `principle-laziness-protocol/SKILL.md`，列出本次范围内可删的现有复杂度（死代码、spec 没要求的校验、空壳引用），先删再加。

按可观察结果推进，每片调用 `bdd`，复用能区分正确和错误结果的检查。技术负责人需要委派时调用 `delegate-ticket`，交出基线和本片设计，收齐证据再集成。常跑类型检查和单个测试文件。

这一片不是一眼能看完的几处编辑时（批量修改、迁移、分析、验证），按运行时目录完整读取 `principle-build-the-lever/SKILL.md`，先写能重跑的脚本、codemod 或生成器，用它完成或证明这片工作。

完成条件：每条验收都按 `bdd` 选定检查或说明缺项，留下运行记录或不写测试的理由；已删项列出，没有可删项时写“无”并列出检查过的范围。

## 3. 真实运行

验证按层叠加：类型、lint 与 API 设计先排除一类错误，测试和真实运行证明行为，形式验证只给真正需要的部分。

1. **入口清单**：列出本次改动的 Interface 的全部调用方和公开入口，逐个确认接上了新合同，过期的断言和文档同步修改。
2. **E2E**：按入口清单和项目的场景注册表选相关场景，判断不清时用 `blast-radius`。大重构跑全部能跑的场景。被 skip 或因前置缺失未执行的场景不算通过，列为缺口。
3. **形式验证**：改动触及项目 `formal-verify-<area>` 覆盖记录里的文件或函数时，必须运行。模型检查报告的路径要在真实代码上复现，复现不了先怀疑模型。它只证明实现符合模型里的规则，规则是否符合意图由用户判断。核心链路上有测试难以穷举的承诺（并发、重试、幂等、状态机、资金、去重）且没有覆盖时，在交付说明里提议 `create-formal-verification-skill`，不在本次创建。
4. **全量测试与 CI**：结束前跑一次项目的完整测试命令，以及项目定义的 canonical CI 或检查命令。

完成条件：每项检查都有命令和结果，结果读自真产物（运行中的功能、实际值、diff）：按运行时目录完整读取 `principle-prove-it-works/SKILL.md`，编译通过、子代理自述、文件时间戳不单独算通过；入口清单已逐个确认；未跑的列出原因。

## 4. 对账

先做消融：按运行时目录完整读取 `principle-minimize-reader-load/SKILL.md`，逐项尝试移除或内联本次新增的层、抽象和状态，用第 3 步的同一组检查对比。检查仍通过、且读者负担不增，就保留简化；否则恢复。无法验证的项保留并标为 Unknown。报告每项的去留和依据。

再逐条核对：每条验收对应哪项检查、结果是什么。对不上的先补实现或检查；确实做不到的列为缺口，不改写验收去迁就实现。

完成条件：每条验收都有检查与结果，或列为缺口。

## 5. 审查

审查单位是 MMF（取舍见 repo://docs/adr/0022-one-review-per-mmf.md）。按本次范围选一条：

- **整个 MMF 已完成**：对账完成后调用 Skill `code-review`。fixed point 取 MMF 第一张票开工前的 SHA；本次就是整个 MMF 时取第 1 步记下的 SHA。spec 源是 MMF 的 Spec 与各票验收清单，入口清单和对账结果作为证据，一并交给它。
- **只是 MMF 中的一张票或一部分**：跳过本步，直接提交；MMF 最后一张票完成时再审。
- **没有 spec 的独立小改动**：跳过本步，靠第 3 步的检查交付。
- **编排派发**（packet 带 Lane ID）：审查由编排器在 MMF 收口时调度，跳过本步。

只有一轮。按严重度处理 finding：

- **P0/P1**：写出根因，修复并排查同类位置。把 finding 的反例加进测试或保留为命令，确认它变绿，再跑一次完整测试与 CI 命令。不开复审。
- **Spec 缺口**：交用户收紧 spec 措辞，按收紧后的验收对账。编排派发时不交用户：把缺口与证据坐标写进工件，以 `LANE_DONE <lane> BLOCKED needs-decision:spec-gap; <工件路径>` 结束。
- **P2**：按项目约定查重。已有同类时引用链接或登记位置。用户已授权写入相应 tracker 或加固清单时登记新项。缺授权时，在报告列为待登记项，写清触发场景、影响、证据坐标与修复方向。
- **P3**：留在报告里，不处理。
- **反例修不绿**：停止，不提交成功结论。用 `postmortem` 记录已确认的失败教训，用 `retro` 提出环境改动建议；把两者的结果和未解决的问题交给用户。

完成条件：跳过本步时写明属于哪一条；审查过时，每条 P0/P1 的反例已变绿并留有命令与结果，每条 P2 都有 issue 链接、登记位置或待登记项，最后一次修复之后跑过完整测试与 CI 命令；或已经按上一条停止并交给用户。

## 6. 提交

按授权用 `git-commit` 把工作提交到当前分支。交付说明写出验证命令与结果、复用既有检查的理由和剩余缺口。在最终干净提交上核对实际结果。集成提交发生变化时，重新绑定受影响的检查与 `code-review` 结论。

在第 1 步的原场景和已批准检查上补入最终集成 SHA、所有已派合同及回执，组成 `MmfPlan`。独立执行整个需求时 `briefs` 和 `evidence` 都用空数组。按[交接合同](../to-tickets/references/delivery-contract.md)填写集成提交的 `observations`、门禁与 `code-review` 实际两轴回执，在目标仓库根向 `node <本 Skill>/scripts/implement.js` 输入 `{input: plan, record}`。交回 `MmfVerdict`。`return` 时指出具体场景、预期、实际结果和责任人，修复后在同一 Seam 重验。票或 MMF 已获验收且已合入目标分支、且具备 tracker 写权限时，同步更新该直接 Issue 状态并回读确认（存在外部上线验收门时保持待验收并说明）。
