# To Epic

从对话、大需求或已有 Epic 出发，定下要交付的用户结果，解决影响拆分的决定，交付一份 Epic 计划。MMF 是验收、合入与上线的单位，一个 MMF 对应一份 Spec、一个 MR；每个候选之后由 `to-spec` 写成一份 Spec。产品源码保持只读，本 Skill 交付规划和交接材料。

## 1. 定目标，推进当前问题

1. **定目标。** 写清谁最终能做什么、怎么验收、范围和不变量。读取目标项目的 instructions、术语、tracker 约定和与目标有关的代码、验收入口及 ADR。引用了需求或已有 Epic 时，先读正文、评论和已有 Spec，沿用原坐标和仍有效的决定。目标说不出专业名称、GLOSSARY 也没有对应词条时，停下请用户运行 `/reframe`，用重写后的描述续接；编排调用时以 `NEXT: blocked-human 目标缺专业术语，需用户运行 /reframe` 交回。
2. **找当前能解的问题。** 先扫过整个需求，找出答案会改变范围、首个 MMF、验收或依赖的问题。能写清的问题，注明它影响哪个决定、还等什么。尚不能问清的未知留在受影响的候选或范围。先做前提已齐、最能影响当前拆分的一项。
3. **按问题选动作。**
   - **查事实。** 仓库代码与现有能力用 `investigate`，外部事实用 `research` 查一手来源。事实可查时先自行取证。
   - **拷问决定。** 只有用户能裁决的目标、范围或业务语义，用 `grilling` 分轮询问。只问当前前提已齐的问题，给出推荐和它会改变的验收或拆分。
   - **做原型。** 某个行为、交互或可行性只能靠具体样例判断时，用 `prototype` 在隔离临时目录做能回答该问题的最小试验。体验取舍把原型交用户判断，可行性用实测回答。
4. **记下答案，再选下一步。** 把结论、依据和它改变的决定写回 Epic 草稿。每得到一条证据或裁决，就重新判断哪些问题可以推进。目标和首个 MMF 已可验收时直接切分，远期未知随候选保留。拆分或排依赖时发现会改变当前决定的新问题，回到本步处理。

拆分前，按运行时目录定位并完整读取 `codebase-design/SKILL.md`，沿用 Module、Interface、Implementation、Depth、Seam、Adapter、Leverage、Locality 的定义。依赖缺失时点名路径和受影响决定，保留为未就绪。

**完成条件：** 目标和范围可核对，首个 MMF 的选择和验收有依据，每个会阻断当前拆分的未知已解决，或已写明卡住的决定与解除条件。正好是一个 MMF 时，按第 5 步的交接写法交给 `to-spec`。

## 2. 选首个 MMF

从用户主线里选择核心、小、能验证关键未知的一条完整路径。缩用户群、数据范围、规则或格式，使这个 MMF 能完整验收，并切不出两个各自能单独上线且有人用的部分。

写清谁从哪个入口做什么、得到什么结果，以及验收证据。分别说明要验证用户需求、技术贯通还是交付能力；已有可靠答案时直接做最小完整交付。能由更小探针回答的可行性问题先探测，探针产物单独标明。

对本片开放的行为，保留金额、授权、数据等实际不变量；验证规模与当前暴露面相称。

**完成条件：** 首个 MMF 有完整用户结果、明确验收和选择理由；阻止它成立的未知已有具体问题与解除条件。

## 3. 展开后续候选

沿用户活动、业务规则、路径、数据或输入方式逐步加厚。每个候选指回 Epic 的目标，并过两条切分测试：

- 上限：存在一种切法让每半都能单独上线且单独有人用，就拆成两个 MMF；切不开就是一个 MMF，不论大小。
- 下限：整体自己上不了线的部分不足一个 MMF，并进用到它的 MMF 作为 ticket。

多个 MMF 共用的使能工作（如一次数据库迁移）单独上线没人用，放进第一个用到它的 MMF，作为结构票，并写明服务的业务结果、保持的不变量与完成条件。

按 `codebase-design` 检查当前及准备并发的候选：相关 Module 的职责和状态 owner 清楚，复杂度收敛在拥有它的 Module，小而完整的 Interface 提供能力，主要行为测试与调用方穿过相同 Seam。优先复用已有 Module 和 Interface。

MMF 与 Module 不要求一一对应。远期候选保留结果、依赖和未知，临近执行再细化。

**完成条件：** 每项已批准结果都有候选或已有能力承接；每个候选写明两条切分测试的答案与依据；延后或取消有明确范围决定；每个当前候选有可核对的验收，远期未知保持可见。

## 4. 连阻塞边，排开工波次

为每个 MMF 候选分配稳定标识。续接、调整顺序和关联已发布 Spec 时复用原标识。
逐个候选写 `Blocked by`：它等哪些 MMF 或外部前提，没有就写 `无` 和一句依据。每条边写清依赖的 Interface、能力或必须先取得的反馈，指出提供者和解除证据，并定类型：

- **开工**：前提交付前本候选不能开工。前提的反馈会改变本候选的范围、业务口径或验收，或者所需 Interface 现在对不齐。只等受影响部分，写明观察结果会改变哪个决定。
- **上线**：共享 Interface 已对齐、写入可隔离，本候选可以并发开发；验收与上线等前提的真实能力、数据、权限或迁移状态就绪。受控 fake 或样例的证据只覆盖其实际验证范围。

普通文件重叠记录为冲突风险，不连边；共同状态、不变量或顺序约束按实际影响连边。

按开工边排波次：没有未解除开工边的候选组成当前 frontier，彼此并发开发；其余候选按开工边串联。远期候选的边按需细化。

**完成条件：** 每个候选都有 `Blocked by`（含 `无`）；每条边有类型、依据与解除证据；开工边无环；当前 frontier 已列出，受阻候选有等待点。

## 5. 保存、交接与续接

记录整体目标、范围与不变量、MMF 候选表、开工波次和待决定事项。调用方传入 `planning_mode: auto` 且原目标与验收有来源时，自主拆分可独立交付的 MMF，记录前后划分、拆分理由和证据坐标。独立调用或沿人工计划审核合同时，首次确定目标与拆分取用户确认。获批范围内继续细化未开工的候选与依赖。

新增、删除或改变已批准结果与验收、关键业务语义取舍、超出现有授权的成本或不可逆影响，交用户决定；被编排方调用时以 `NEXT: blocked-human <待决定事项>` 交回调用方。已开工 MMF 受影响时先协调对应工作与 Interface，再更新候选和依赖。

**先发布，再交接。** 拆分决定已记录、tracker 已配置且已有发布授权时，按项目约定创建或更新 Epic Issue，读回正文、关系与链接，返回标题、标识和 URL。已确定的计划和决定持久化到 Issue，调研或原型证据用链接引用。缺发布授权或 tracker 坐标时交回草稿，编排调用报 `NEXT: blocked-human` 并注明缺项。

更新已有 Epic 前，按交付链路的 Epic 认领合同取得写入权，重读正文与关系；已有持有者时由该 coordinator 写回。当前无法核实认领时，在会话交付待写内容。更新保留既有 Spec 链接，实际持有者同步两端已有 Spec 的原生依赖，并点名需更新的 Dependencies 节。部分失败时报告已成功坐标及剩余动作。

**交出当前就绪的 MMF。** 列出 Epic Issue 或草稿坐标、代码基线、范围、验收、相关 Module/Interface、开工波次、依赖和已有决定的指针。标明仍受开工边阻塞的候选及等待点。编排方调用时，以 `NEXT: to-spec <候选与理由>` 交回。独立调用时，将已发布 Epic 链接交给用户选择的支持 Epic 的入口；只推进单个 MMF 时同时给出其稳定标识。所选入口要求先有 Spec 时，由能取得 Epic 认领的 coordinator 安排 `to-spec`。未形成 Epic 的单个 MMF 可独立交给 `to-spec`。Spec 发布后回链 Epic。

**完成条件：** 规划产物可读回或明确未发布；当前可推进候选、等待点和交接输入齐全。规划完成、首个 MMF 完成与 Epic 全部结果验收分别报告。

## Epic 产物

正文保留目标、范围与不变量、候选表、开工波次、已决定事项和待决定事项。查证、拷问和原型的结论写到受影响的决定或候选，证据用链接引用。

| MMF 标识与候选 | 用户结果与验收 | 切分依据（切不开 · 整体单独上线有人用） | 相关 Module / 共享 Interface | Blocked by（类型 · 依据 · 解除证据） | 下一动作 / Spec 链接 |
| --- | --- | --- | --- | --- | --- |

续接时用新证据或反馈重走受影响的决定，只重切受影响的候选。整个 Epic 的交付完成由所有已批准结果的实际验收证明。
