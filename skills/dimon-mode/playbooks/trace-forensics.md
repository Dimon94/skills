# 已有产物取证诊断

你只负责从既有采样产物产出带出处的诊断，不修改产品代码。与面向活进程的 [`runtime-forensics.md`](runtime-forensics.md) 不同，这里的产物是固定数据集：直接分析它，不试图重跑复现现场。确认原因后再交回 [`bug-fix.md`](bug-fix.md) 或 [`perf-issue.md`](perf-issue.md) 修复。

1. **识别格式并用通用工具加载。** 区分 `.cpuprofile` / Chrome trace `.json(.gz)`、`.heapsnapshot`、macOS `spindump` / `sample` 等格式，选用对应通用解析工具。按 `principle-guard-the-context-window`，大产物交给只读子代理解析，主线只保留结论与查询坐标。完成条件：确认格式且成功加载。
2. **先转成可查询结构再读。** 把 trace、profile 或堆快照导入 SQLite（每个采样、调用帧或堆节点一行），先建立可查询表再下探，不靠人眼扫原始 JSON/文本。完成条件：拿到可重复查询的结构化表与摘要统计。
3. **用查询收窄到根因。** 性能问题查自耗时/总耗时最高的帧并沿调用树走到热路径；内存泄漏沿持有链追到 GC 根；spindump 找卡在 CPU 上或阻塞的线程及其等待原因。完成条件：锁定关键帧、持有链或阻塞线程。
4. **用产物符号归因回源码。** 把热帧或分配点映射到文件、符号与行号。**没有源码映射的帧还不算诊断**：解出对应 sourcemap / 符号表，或明说产物未携带符号信息。完成条件：给出精确源码坐标，或显式标注缺失符号。
5. **按是否有成对产物校准置信度。** 若有改前/改后或正常/异常成对产物，做 diff 确认机制；没有成对产物时，结论必须显式标为“产物支持的最强假设”，不写成已确认根因。
6. **交回修复入口。** 未经要求不顺手修复；带着证据交回 [`bug-fix.md`](bug-fix.md) 或 [`perf-issue.md`](perf-issue.md)。

回复写五项：产物路径与格式；缩减出的结论；源码坐标（或缺失符号说明）；中间查询产物路径；是否有成对产物 diff 确认。
