# 爬坡

对着一个可测量的指标持续迭代到目标。一次性的修复走 [`bug-fix.md`](bug-fix.md) 或 [`perf-issue.md`](perf-issue.md)。

一次一个改动，一次测量，留下或回退。没测过的改动不叠加。按 `principle-prove-it-works`，看代码得出的“应该更快”不算赢。

1. 定指标前先摸清负载。用 `how` 追目标路径，列出真实负载的维度（数据量、历史长度、状态、并发），选一个能复现用户抱怨的用例。没有用例能复现时，先修复现，不爬坡。然后定三样：一个指标、哪个方向算更好、一个停止条件。停止条件是可检查的判定，目标加最少尝试次数，例如“比基线好 50% 以上，且至少试 10 轮”。用户给了数字就用用户的，没给就和用户商定。
2. 按 `principle-build-the-lever` 建测量工具，证明它灵敏，再冻结。准备几组有对比的真实负载：目标用例复现症状，轻的用例明显不同。分不开时改负载或改指标。冻结前按运行时目录完整读取 `benchmark-checklist/SKILL.md` 逐问核对。工具每次打印错误数和完成的工作量。一条可重复的命令输出指标，采样次数够盖过噪声（取 N 次的中位数）。完成条件：记下基线，回归检查跑绿一次，之后不再改工具。
3. 建决策日志 `decision.tsv`，每次尝试一行：编号、假设、改动、改前、改后、差值、测试、结论（留下或回退）、备注。每次尝试前先读它。日志不进仓库，加进忽略清单。
4. 每个假设写明具体机制，依据来自第 1 步。“把 X 挪出启动路径，因为它挡住首屏”算；“试试加缓存”不算。指标是性能时，按 [`perf-issue.md`](perf-issue.md) 第 2 步的七条顺序排假设；只借顺序，不借那一步的“达标就停”。
5. 循环，每轮一个假设：
   - 改动范围收紧到这一个假设。互不相干的假设要并行时，按 `principle-separate-before-serializing-shared-state` 各开一棵工作树。
   - 用冻结的工具测改前改后，再跑回归检查。
   - 指标变化超过噪声且回归检查全绿，才留下；否则整个回退。
   - 每个留下的改动按 `git-commit` 单独提交。
   - 不论留下还是回退，都在日志里记一行。
6. 连续几轮被回退时换方向：换一类假设、把几个差一点的合起来、重读源码，或试更激进的做法。正确和简单排在数字前面：破坏行为的提升要回退；按 `principle-laziness-protocol`，守得住数字的简化要留下。
7. 停止条件满足，或剩下的想法收益都很小时停。不放宽停止条件。还有便宜的假设没试就不停。卡住时告诉用户卡在哪。

回复写六项：指标与目标；基线到最终值及百分比变化；跑了几轮（留下几轮、回退几轮）；每个留下的改动一行；`decision.tsv` 路径；下一个最值得试的想法。
