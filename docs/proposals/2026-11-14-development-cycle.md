# 开发周期管理接入方案

状态：业务方案与三项 MMF 拆分已确认；[Epic DD-539](https://linear.app/erplus/issue/DD-539) 已发布，[本地 Epic 记录](2026-11-14-delivery-cycle-epic.md)可续接；[M1 Spec DD-540](https://linear.app/erplus/issue/DD-540) 已发布，验收 Seam 已确认；未实现、未修改周期配置。

本地记录为发布快照；后续状态和合同修订以 Linear 为准。

## to-spec 的 MMF 边界判定

Kimi K3.1 Pro 已完成短任务判定，实际模型回读为 `magpie/junbo/kimi-k3.1-pro`。两次完整起草因连接重置失败，短任务只完成 MMF 判定，不代表完整 Spec 或发布就绪审查完成。

- **整体独立上线有人用：是。** 用户可以获得跨 MMF 的本周工作集合、显式剔除、未完结转及正式交付结果。
- **能切成两个各自独立有用的半片：是。** 周期归属维护可独立提供本周范围与结转；按 Spec 和 main 证据核对正式交付可独立提供可信的周交付清单，不以 Cycle 归属为判定前提。
- **结论：多个 MMF，最少两个候选。** 按 to-spec 第 2 步停止，不将整个首版发布成一个 ready-for-agent Spec。

| 候选 | 独立用户结果 |
| --- | --- |
| M1：周期归属与结转 | 正在推进的工作默认纳入本周，保留显式剔除和跨周现场，得到可信的本周开发集合 |
| M2：正式交付对账与周报 | 按 Spec、main 合入及周截止证据生成去重的交付结果，复用已有 weekly-report 表达 |

以上是最初的切分候选，不是两个已定稿的 Spec。当前候选、顺序与共享判定 owner 以 [Epic 拆分草稿](2026-11-14-delivery-cycle-epic.md#mmf-候选与顺序)为准；不能在多个 MMF 中复制正式交付口径。

## 目标与范围

在 my-skills 的普通开发链路中增加一周开发周期管理；delivery-pipeline 可以接入，但不是使用或验收前置。周期收纳正在推进的工作，按 MMF 统计正式交付，并将未交付工作滚入下周。

既有依赖驱动的自动派发、实现、集成、测试、审查和授权边界继续由原链路拥有。周期归属不成为启动或继续执行的 gate，不限制 MMF 大小、执行时长或并发额度。

本方案只涉及开发管理、任务归属、交付证据和开发周期报告。

## 已确认的规则

1. **周期为一周。** 个人项目与 JUNBO 分别管理、分别报告，规划时共同考虑实际可用容量。
2. **进行中默认纳入。** 本周正在推进及本周新开始的工作进入本周 Cycle；不先预测能否本周完成。尚未开始的全部 Backlog 不自动灌入。
3. **允许主动剔除和调整。** 记录移入、移出及其原因，自动同步不能无声撤销用户选择。
4. **保留自动调度。** Cycle 不增加逐项人工启动，不创建第二执行队列，不因跨周重启任务、重建分支或重置既有执行状态。
   **普通开发同样触发。** 不使用 delivery-pipeline，正常开始／恢复开发与合入 main 时也要维护周期；不能要求用户先使用编排器。
5. **按 MMF 统计交付。** Cycle 可展开 Spec 父 Issue 与执行 ticket；正式交付按所属 MMF 去重。Epic 保留跨周期总览，不冒充本周可完成的一个交付单位。
6. **按 Spec 与主分支证据判定。** 正式交付必须满足该 MMF 的 Spec 交付要求，并有实际 main 合入证据；仅进入 Integration 分支不算正式交付。实现、集成、合入、上线和业务验收分别陈述，Spec 要求的后续条件未满足时不提前记为正式交付。
7. **未交付自动结转。** 周期切换时，仍未达到正式交付标准的工作进入下一周，保留其原 Issue、MMF 归属、分支、执行现场和阻塞原因。已完成子票不当作下周新交付重复计算。
8. **周界限采用北京时间。** 周一 00:00 开始，至下周一 00:00 截止，采用左闭右开区间。周一 08:00 整理上一周期报告；00:00 后完成的交付归新周期，不为出稿时间倒算上一周。

## 最小职责划分

建议新增 `skills/delivery-cycle/SKILL.md`，作为开发周期管理的唯一行为 owner。

| 职责 | Owner | 交接内容 |
| --- | --- | --- |
| 本周归属、显式剔除、跨周结转、按 MMF 汇总 | delivery-cycle（拟新增） | 平台周期、原 Issue 引用、正式交付证据及缺口 |
| 普通开发的开始／恢复、实现与验证 | 本库既有开发及恢复入口 | 原 Issue／MMF 身份与真实开发状态 |
| 使用编排器时的依赖、就绪 frontier、派发、恢复、集成、测试与审查 | 可选的既有 delivery-pipeline 核心及所属 transport | MMF／Spec／ticket 坐标与当前执行事实 |
| main 合入及发布／验收事实 | 原项目与既有 closeout owner | 实际合入回读、Spec 验收结果及后续交付记录 |
| 开发周期报告的表达 | 既有 weekly-report，按需引用 | 已核对的本周交付、推进、阻塞、范围变化与结转 |

周期归属保存在原管理平台。执行和验收事实继续来自原项目与原 Issue；报告是带截止时间的证据快照，不建立第二份可变任务状态或本地任务数据库。

周期职责跨多个 MMF，需要独立运行“核对本周／周期结转／周期报告”，并同时服务普通开发与可选编排器，因此拥有独立 Skill。各开发入口只调用同一 owner，不复制周期规则。

## 交接顺序

### 工作开始或恢复

1. 普通开发入口或可选编排器依据既有合同确认可推进的工作。
2. 周期维护读取原 MMF、父子 Issue、目标团队及真实周期，把正在推进的工作关联到当前周。
3. 显式排除项保留用户选择，其余工作继续既有自动派发。

周期同步失败时显式报告未同步，不声称已纳入；失败不改变原链路的执行资格或启动第二次任务。

### MMF 交付与回读

原 closeout owner 完成其已获授权的操作后，周期维护回源核对 Spec 和 main 合入证据。本地 main 合入与 PR 合入后的 parity 读回都要覆盖，不以经过 pipeline 为条件。ticket Done、Integration 验证通过或 Issue 正文自称完成，都不能单独证明 MMF 正式交付。

任务状态与交付证据冲突时标注具体缺口和 Unknown，交原状态 owner 核实，不由周期 Skill 伪造 main 合入或擅自完成发布。周期操作也不新增 push、合并或部署权限。

### 周期切换与报告

1. 按原周期截止时间核对实际交付，区分本期新完成与上期结转。
2. 将仍未正式交付且未被显式剔除的工作关联下一期；相同结转重复运行不重复创建周期、任务或成果。
3. 报告覆盖本周全部实际开发成果与进展，显式排除 Cycle 的工作如有实际成果也说明来源；分别呈现正式交付、进行中、阻塞、范围变化与结转原因。
4. 08:00 整理报告时继续以 00:00 为交付统计截止，不把新周期进展计入上期正式交付。

周期维护不为结转重新拆 MMF、重开任务、丢弃旧证据或重置预算。

## 平台接入

首个接入目标为当前 Linear 开发任务。先读取团队时区、周期长度、Started／Completed 自动归属和未完成滚动设置，复用满足合同的原生能力。

原生能力不能覆盖的本仓交付口径，由同一周期 Skill 定向对账；不复制平台已具备的周期引擎。父项未跟随子项进入进行中、Done 缺 main 证据及用户剔除等情况必须留下明确处理结果。

Jira Sprint、禅道迭代等复用同一开发管理语义，但第一版不承诺已接入其 API；没有完成实际适配时明确报告未支持，不伪造平台同步。

Linear 官方说明：周期按 Team 时区的 00:00 切换，支持自动纳入 Started／Completed Issue 和未完成滚动。具体启用结果以平台读回为准。

来源：[Linear Cycles 官方说明](https://linear.app/docs/use-cycles)，章节 Starting day of the week、Cycle automations。

## 建议随整体方案确认的两项约定

- **剔除持续有效，直到用户恢复纳入。** 不在下一次同步或跨周时悄悄加回。具体标记使用平台可持久读取的原生字段或标签，实施时核对现有机制，不新增本地副本。
- **08:00 是报告时点，不等于已经设置后台任务。** Skill 提供报告动作；本次先不创建定时任务或自动发布。需要自动唤醒时复用实际宿主的定时能力，再单独核对目标与授权。

## 验证案例

| 输入或动作 | 应观察到的结果 |
| --- | --- |
| 一项预计跨周的 MMF 已经开始执行 | 父项及相关执行工作进入本周，既有派发继续，不被预估工期筛掉 |
| 全程未调用 delivery-pipeline，正常开始／恢复开发，并经本地或 PR 路径合入 main | 仍触发同一周期维护和交付核对；不需要启动编排器 |
| MMF 有三张 Done 子票，但尚未完成 Spec 或合入 main | 三张子票不形成三次正式交付，MMF 仍未正式交付 |
| 仅有 Integration 合入和测试通过 | 报告为已集成；不能记正式交付，未完成项继续结转 |
| 达到 Spec 要求且 main 合入完成 | 所属 MMF 只计一次正式交付，重复扫描不重复计数 |
| 用户主动剔除后再次同步或跨周 | 保留显式剔除，原自动开发不被停止 |
| 周一 00:00 前未完成，00:30 完成，08:00 出稿 | 上期记录结转；正式交付归新期，出稿不改统计截止 |
| 相同周期重复同步、结转和出稿 | 不重复建 Issue／Cycle，不重复移动或累计交付，保留既有证据 |
| 周期 API 不可用或权限不足 | 明确同步失败和未验证范围，原 pipeline 的派发、预算和恢复语义保持 |
