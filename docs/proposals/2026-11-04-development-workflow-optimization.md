# 开发框架优化方案：完成度、审查收敛与验证成本

Status: proposed

范围：汇总现有研究，供选择优化顺序；CI/CD 按用户要求暂不处理。本页不授权修改运行规则。

## 当前判断

建议先优化 **审查发现项的处置、修复后的复核范围**，再收敛测试和防御代码的成本，并用真实入口验收检查交付完成度。优先修改已有 owner 的规则与交接，不增加审查阶段、评分平台或新的同类 Skill。

`to-epic` 已提交并安装，承载 Epic → Spec 的切分。它是本轮已完成的单独成果；真实复杂 Epic 的行为效果仍待验证。当前 `to-spec`、`to-tickets`、CodeReview 和测试规则尚未因这些研究而改造。

## 优化清单

| 顺序 | 优化对象 | 目标 | 主要落点 |
| --- | --- | --- | --- |
| 1 | Review 发现项如何影响交付 | 必须修复、可选建议、待取证各有清楚依据 | code-review 的输出与处置；目标项目质量规范 |
| 2 | 修复后及多层审查的证据复用 | 新版本得到适用独立结论，同时保留仍有效的覆盖 | code-review、gh-merge-pr 及其调用方的交接 |
| 3 | 测试的必要性与充分性 | 少量有区分力的检查保护当前需求，减少重复装置与低价值穷举 | 已有 test-review、目标项目测试规范 |
| 4 | 防御代码与复杂度增长 | 防护对应真实输入、权限、状态或副作用风险 | 实现时的边界设计与 Standards 审查 |
| 5 | Spec 的实际完成证据 | 尽早发现遗漏、接线和真实运行差距 | 既有 Spec 验收记录、实现交付与项目 verify 入口 |

### 1. 明确 Review 发现项的处理方式

当前规范已经要求场景、影响和证据，并区分 P0–P3；通用坏味道也被标为 judgement call。缺口是严重度、建议与“是否阻断本次交付”之间的关系不够明确。质量规范还引用了不存在的根 AGENTS `<stage>`，需要修正这个判定入口。

建议每条发现说明：本次触发条件、实际影响、依据，以及是必须修复、可选建议还是待取证。安全、资损、持久数据、已接受验收和有原则依据的设计问题保留阻断能力；低影响罕见组合、偏好与已被反证的重复防护按实际影响处理。

技术事实由 agent 定向取证，不因每个陌生评论都要求用户裁决。只有产品语义、范围、授权等真实取舍再交用户决定。同根因共享修复与复现，Standards/Spec 各自保留依据。

验证方式：用实际发现项核对哪些评论应要求代码修改、哪些可以说明后收口。越权、重复出款、数据损坏及真实验收缺失仍被拒绝；没有依据的命名偏好和重复校验不会持续扩张当前 Spec。

### 2. 协调新版本结论与旧证据复用

当前 `code-review` 已允许修复后复核受影响轴/范围；`gh-merge-pr` 让旧 Packet 与结果随 head 失效。这两条可以兼容，不能直接据此断言每次都全量重审。

建议修复交接至少说明修复 diff、对应 finding、受影响行为与证据；reviewer 更新 Packet，检查修复及邻接风险，说明哪些覆盖仍有效，再给当前版本结论。新增行为、重设计、依赖变化或冲突解决需要重新判断影响范围。只搬旧 PASS、只更新 head 字段或只凭 patch-id 放行都不足够。

跨层同样区分职责：单票、集成和 PR 审查可能各有独有覆盖。先明确每层检查什么、已消费什么证据，只有证明覆盖相同且对当前输入仍有效时才省去重复工作，不预先删除任何一层。

验证方式：比较“小修复”和“共享 Interface/依赖改变”两种情况。前者能只补必要证据，后者会扩大核验；两者都有当前版本的独立结论。真实 bug 持续修复，轮次不作为自动通过条件。

### 3. 执行已有测试价值取舍，校正机械阈值

`test-review` 已有高价值优先、低价值未覆盖不自动 FAIL/Unknown、保护有争议才消融等规则。应让这些现有判断真正影响补测和删测意见。

每次补测说明它拒绝哪个与当前 Spec 有关的错误实现，以及现有检查为何发现不了。优先扩展公开 Interface 附近的既有检查，测试实际结果和关键副作用；替身放在需要隔离的外部位置，避免 mock 被测逻辑本身。

数量、行数和覆盖率只提示成本。“默认主路径加关键失败路径”是取舍起点，不能推导最多两例；少行权限逻辑也可能需要多身份检查。重复输入、内部调用顺序、无新保护的参数组合和庞大 fixture 优先缩减；必要慢测试先优化装置。

验证方式：每个保留或新增测试能指出被拒绝的具体错误实现；合并/删除建议能说清替代覆盖或接受的低价值损失。满足当前验收和实际新增风险后停止扩张，不新增通用测试筛查平台。

### 4. 让防御代码说明自己防的真实问题

集中处理外部输入与真实信任变化；内部使用已校验值。身份、资源归属、异步状态变化以及副作用前的检查可能构成新的必要校验点，不能只凭类型存在就删除。

新增 catch、fallback、重试、重复校验、锁或恢复机制，要指向当前可触发的失败及其损失。现有保障已覆盖且没有新风险时，不为安静增加保护。优先用清楚的 Module 职责、小而完整的 Interface 和必要 Seam 收敛复杂度。

验证方式：保留当前越权、金额、状态和副作用风险的检查；已经由唯一解析器保证的内部非空值不再层层复查。等价设计选择尊重作者偏好，有实际 Depth/Locality 影响的问题按工程依据处理。

### 5. 把“实现完成”核对到 Spec 的真实结果

把已有验收要求、负责实施的工作、最终入口和结果证据用链接关联，复用原产物，不另建状态台账。关键主线至少从真实入口验证结果；涉及写入、外发或金额时核对相应副作用。其他规则使用合适的既有 Interface 检查，不要求所有情况都跑 UI 端到端。

项目已有 verify Skill 或测试入口就直接复用；缺少可驱动的真实入口时再使用已有生成机制。HTTP 200、截图、全绿、合入和部署分别说明各自证明的范围。

验证方式：首次验收能指出已批准结果的当前证据；缺口保持未完成或未验证。记录人工补接线、补行为发生在哪里，再判断剩余问题属于 Spec 漏项、粒度、集成还是环境。当前没有历史任务数据，不能把用户所述 80% 直接归因于拆票。

## 推荐实施顺序与取舍

第一批做 1 和 2：它们直接针对当前审查文本和交接规则，改动可以限定在已有 owner 中，先验证“噪声驱动修改”和“重复重审”是否减少。

第二批做 3 和 4：把测试及防护的必要性接到审查处置上，保留关键保障，避免 Review 继续制造新的低价值工作。

第 5 项贯穿一次真实 Spec 的试用，用来检查少做重复验证后是否仍能交付完整结果；根据实际缺口再决定是否需要调整 `to-spec` 或 `to-tickets`。当前不预设它们需要整套重写，也不预设所有分层审查都是冗余。

试用只记录三类事实：每轮新增真实问题与重复噪声、被复用和重做的审查/测试覆盖、首次验收遗漏与人工补齐。暂不建设指标系统，不承诺具体节省比例。

固定轮次自动通过、固定测试数量、固定十条 live 验证、按“报错是否在 diff 内”归因，都不作为本方案的通用判据。已实测证明只改 provider 也能使未改 consumer 失败，见下列审查收敛报告。
