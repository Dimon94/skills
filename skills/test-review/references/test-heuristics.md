# 测试启发式

职责：帮助 `test-review` 定位测试价值问题。项目规范与已接受需求决定合同；以下问题是由作者理念推导的审查启发式。研究来源与访问限制见 [研究记录](../../../docs/research/2026-10-09-test-value-principles.md)。

## 先还原用户结果

为受影响场景写出：**角色/需求 → Given 条件 → When 真实动作 → Then 可观察结果 → 独立预期 → 能拒绝的错误实现**。结果可以是输出、持久状态、公开错误或外部副作用，也包括“失败后没有写入/扣费”。前置条件只保留影响结果的部分。找不到需求依据时写 Unknown，继续核对机制。

BDD 澄清业务行为；TDD 是开发反馈过程；单元、集成与 E2E 描述测试范围。这些维度分别判断。GWT 语法不保证示例有价值；业务测试可以通过组件入口运行。函数级金额规则可能保护用户结果，UI E2E 也可能只观察静态标题。执行层级仍遵守项目测试规范。[North：What's in a Story?](https://dannorth.net/blog/whats-in-a-story/)、[Adzic：Specification by Example 回顾](https://gojko.net/2020/03/17/sbe-10-years.html)、[Fowler：Business-Facing Test](https://martinfowler.com/bliki/BusinessFacingTest.html)

例如“购买成功”应按该需求核对金额、交付或权益读回；“导出成功”应检查导出内容满足选择范围；“保存成功”应检查重新读取的状态。具体结果由 Spec 决定，不能把这些例子变成所有项目的检查清单。

## 用有名的概念反问

| 关键词 | 审查动作 |
| --- | --- |
| 二八取舍 | 先按 [SKILL.md 的二八原则](../SKILL.md) 选关键测试，再判断补测或缩减。点名主要保护价值与可接受的不覆盖内容，不把所有边界展开成测试清单。 |
| 业务结果 / Business outcome | 点名受益角色及需求产出。把“执行过函数”“出现成功提示”与该测试实际证明的结果分开。 |
| 回归保护 / Behavioral | 指出一个本次需求相关的错误实现，追到会失败的断言。业务错误仍通过是 **假绿 / false negative**。 |
| 独立预期 / Independent oracle | 追查期望值来自需求示例、手算、标准向量或经审核基线，还是复制被测实际值。“独立预期”是本 Skill 的归纳用语，依据 Beck 对复制实际值的批评。 |
| 消融测试 / Ablation | 先读下节的消融方法，再核对移除该测试会损失哪种保护、移除关键业务逻辑会触发哪条失败。不能用“删前删后都绿”代替判别力证明。 |
| 抗重构 / Structure-insensitive | 用等价算法、内部重命名或文件移动反问。合同未变却失败是 **假红 / false positive**；公开协议或获确认的视觉变化不属于等价重构。 |
| 真实边界 / Predictive | 沿真实 owner、调用方与依赖读取测试边界。结果验证与交互验证都可有效；指出替身尚未证明的真实合同。通过预测能力不是部署或业务验收证明。 |
| 稳定反馈 / Deterministic、Isolated | 核对可写数据、时钟、随机、并发与等待。这里的隔离指测试互不影响，并不要求 mock 所有协作者。 |
| 可诊断 / Specific、Assertion Roulette | 失败应指向具体结果。多个断言可以共同保护同一场景；问题在于失败无法定位，不能按断言数量判错。 |
| 净保护价值 | 比较新增保护与运行、误报和维护成本。合并/删除前点名替代覆盖或可接受的低价值保护损失；独有高价值慢测试先优化装置或执行阶段。 |

概念依据：[Beck：Test Desiderata](https://testdesiderata.com/)、[Beck：Canon TDD](https://newsletter.kentbeck.com/p/canon-tdd)、[Fowler：Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html)、[Meszaros：xUnit Test Patterns 第 16 章正式预览](https://www.oreilly.com/library/view/xunit-test-patterns/9780131495050/ch16.html)、[Khorikov：Unit Testing 官方节选与章节地图](https://enterprisecraftsmanship.com/files/Unit-Testing-Chapter-1-Excerpt.pdf)。这些资料支持概念；表中的审查动作是本 Skill 的推导。

## 关键词用于导航

从当前 diff 及其相关测试搜关键词，补读实际值、预期值、生产入口与失败传播。下表各项都同时检查风险与合法合同。不同框架名称不同；找不到关键词也必须沿场景检查。

| 搜索线索 | 要追查的问题 | 有效使用场景 |
| --- | --- | --- |
| `sha256`、`md5`、`digest`、`hash` | 普通源码/fixture 指纹是否只锁定文件不变？预期摘要是否由同一实际结果即时生成？业务错了但摘要检查仍通过吗？ | 标准向量、篡改拒绝、产物完整性、身份或已确认的字节合同。摘要一致只证明对应内容，不自动证明功能正确。 |
| `getByText`、`toHaveTextContent`、`textContent`、`innerHTML` | 只检查永远存在的标签，还是动作后真实状态的呈现？失败流程也显示同样文字吗？ | 金额、选择结果、错误引导、无障碍名称、获确认的文案合同。检查状态来源及真实触发。 |
| `toMatchSnapshot`、`toMatchInlineSnapshot`、golden | 基线由谁审核？是否靠无脑更新把回归变绿？快照锁住公开输出还是内部树形结构？ | 经审核的视觉、序列化或输出合同；用具体差异说明哪个用户结果被破坏。 |
| `readFileSync`、`read_text`、`includes`、源码正则 | 是否只证明源码出现某个词、存在 helper 或固定路径，真实行为仍可错误？ | 真实生成物、解析输入、配置/协议合同；如项目只要求文件存在，结论限定在存在性。 |
| `jest.fn`、`vi.fn`、`mockResolvedValue`、`toHaveBeenCalled` | 是否替换被测 owner 后再断言假结果？是否验证内部协作细节却遗漏真实输出？ | 真实 owner 对外部 seam 的金额、收件人、次数、顺序或失败路由；说明未覆盖的服务边界。 |
| `expect(true)`、`assert True`、`toBeTruthy`、`toBeDefined`、`not.toThrow`、`status(200)` | 断言是否无条件成立、只验非空/无异常，或声称超出实际证明范围？ | 已确认的存在性、错误/HTTP 合同、明确限定范围的冒烟测试。 |
| expected 与 actual 共用被测函数、自动更新 baseline | 两边是否复用同一个错误算法？预期是否来自未经复核的当前实现？ | 独立样例/标准向量、经审核基线；property/metamorphic 检查要有需求支持的不变量，并能拒绝一个具体错误实现。 |
| `waitFor`、`dynamic import`、`collect`、`void onPress` | 局部超时是否混入真实模块冷加载？按钮返回值能否代表整条操作完成？失败后的清理会不会撤销仍在使用的替身？ | 分开模块准备与行为等待；保留真实 owner、业务状态和副作用断言，用受控探针区分超时原因，不靠加大预算结案。 |
| `UNREGISTERED`、`registry`、`owner`、`check:` | 门禁读到需求规定的 owner 吗？合法输入能通过吗？静态解析会丢失校验字段吗？另一 owner 的登记会不会意外放行？ | 对实际扫描与登记范围运行最小正反例；保留治理字段，无法解析时明确失败；错误文案不能代替根因，修接线前不复制同义规则或扩大公共登记。 |
| `skip`、`retry`、`allow_failure`、`catch`、`sleep`、未 await | 关键断言是否未执行，异常是否被吞掉，失败是否未传到 runner/CI？重试是否掩盖真实错误？ | 明确排除的范围、有界等待或外部协调，保留最终失败与缺口证据；按项目规范判断。 |

## 消融测试：证明独有保护

这里的“消融测试”是本 Skill 的操作定义，分两种检查。移除关键逻辑检验判别力与 mutation testing 相近；PIT 官方说明修改返回值、条件或移除调用后，有效测试应识别行为错误，同时提醒等价变异不应当被当成漏测。[PIT：Basic Concepts](https://pitest.org/quickstart/basic_concepts/)

先判断保护价值。消融只用于关键保护或删减有争议的最小场景，不要求每条测试都运行一次。证明有独有覆盖后，仍须按二八原则判断这项保护是否值得承担成本；明确接受的低价值不覆盖无需建立一套 mutation 工程。

1. **选定现实错误**：从已接受需求列出本次要保护的错误，例如漏算数量、跳过持久写入、漏掉权限检查。先确认正确实现能通过，错误实现确实破坏该合同；编译错误、装置崩溃或等价修改不算业务判别力。
2. **消融关键逻辑**：在隔离副本临时移除或旁路这段逻辑。目标测试应因具体结果不符而失败。仍通过时，追查断言、替身与入口；结论限定在这个错误场景。
3. **消融测试本身**：在同一个错误实现和同一执行条件下，对比含该测试与临时移除该测试的剩余集合。含它能拒绝、移除后漏过，证明这项独有保护；两边都拒绝时，列出剩余检测坐标，再核对其他场景、入口和环境后判断是否重复；两边都通过时，说明该错误原本未被保护，改写断言或补回丢失的有效覆盖。部分重叠不能推导整例无价值。

对正确实现而言，有无测试都绿是正常现象，不能据此删除。重叠测试可能分别覆盖不同入口、边界或执行阶段；按实际合同确认其价值。测试易生成不改变门槛：应给出具体需求、能检测的错误与相对现有覆盖的收益，再承担 CI、误报、阅读与维护成本。

默认先做静态追踪；必要时运行一个最小反例，记录原/错误实现、测试选择与发现命令、退出码、失败原因和替代覆盖。执行权限与隔离要求沿用 SKILL.md；无法确定时保留候选并标 Unknown，不要求安装 mutation 工具或遍历全仓。

## 形成可审核的结论

每个疑点给出 **测试坐标 + 需求/规则坐标 + 具体错误 + 现有断言为何漏过或误报 + 最小处理方向**。把运行反例、静态推断和 Unknown 分开。必要时只在隔离副本验证一个错误实现；全仓 mutation、覆盖率目标与格式改造不作为默认任务。

优先保留保护主要业务结果与高影响风险的最小测试集；改写镜像或被替身遮住的关键断言；合并重复场景，按二八原则提出低价值缩减或不覆盖的取舍。旧合同已退役且无独有覆盖时提出删除。审查只提出方向，写入权限沿用 SKILL.md。
