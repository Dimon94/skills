# Epic：Linear 开发周期管理接入开发链路

状态：用户已确认三项拆分与顺序；[Epic DD-539](https://linear.app/erplus/issue/DD-539) 已发布，[M1 Spec 草稿](2026-11-14-delivery-cycle-m1-spec.md)已发布为 [DD-540](https://linear.app/erplus/issue/DD-540)，手动 Skill 验收 Seam 已确认；运行前置待解除，未实施。

本地记录为发布快照；后续状态和合同修订以 Linear 为准。

## 整体目标

普通开发沿用原流程，使用 delivery-pipeline 时继续原自动调度。两条路径都在开始／恢复及 main 合入读回后维护当前周期，不以是否使用 pipeline 作为条件。进行中的 MMF 父 Issue 与 ticket 默认纳入本周 Linear Cycle，保留主动剔除；按 Spec 完整交付要求与 main 实际合入证据核对正式交付，未交付工作跨周结转。周一人为调用，得到按 MMF 去重的开发周期报告。

业务口径沿用[已确认方案](2026-11-14-development-cycle.md#已确认的规则)，不重新开展需求访谈。

## 范围与不变量

- 首版仅 Linear。个人项目与 JUNBO 分别管理、分别报告；管理对象都是开发任务。
- Asia/Shanghai 周一 00:00 切换；周一 08:00 手动整理上一周期，统计截止仍为 00:00。
- 进行中默认纳入，不用预计完工时间筛选；全部未开始 Backlog 不自动灌入。用户剔除持续至明确恢复。
- 周期归属不成为执行 gate。原依赖、自动派发、并发、预算、恢复、授权与交付要求继续由原链路拥有。
- 自动维护必须覆盖本库普通开发入口；delivery-pipeline 是可选调用方，其接入不是本 Epic 的交付前置。
- 正式交付判定只有一个 owner：Spec 要求满足且 main 合入已证实。Integration、ticket Done 和正文自称完成均不足。证据缺失保留 Unknown。
- 原平台拥有周期归属与显式排除；原项目拥有执行、验收和合入事实。报告是证据快照，不建立第二份可变任务状态或本地任务数据库。
- 不重开原任务、不重建分支、不重置执行现场，不重复计已完成子票。周期写入失败显式报告，不能冒充成功或改变原自动派发。
- 不接 Jira／禅道，不新增后台定时或自动发布，不重写周报系统、合并器或平台周期引擎。

## 当前事实与拆分依据

1. 现有 pipeline 拥有依赖驱动的执行、集成、测试、审查和授权下的 closeout；没有远程合入授权时，允许停在已验证的 Integration 分支。
2. 现有 closeout 会核对 summary PR／MR 合入及远端默认分支，不能直接把执行 graph 清空视为正式交付。
3. 既有 weekly-report 已拥有成果核对、分组表达和手动报告流程，可以复用，不新增报告表达 owner。
4. Linear 已有 Cycle、原生自动归属与未完成滚动。具体团队配置、可调用写入能力与显式剔除的持久标记仍需在第一份 Spec 中核实。
5. 本库普通需求通过 implement 开始执行；会话接手按既有恢复入口继续；git-rebase-main 与 gh-merge-pr 分别核对本地 main 合入和 PR 合入后的 parity。它们是普通开发维护周期的现有调用位置。delivery-pipeline 另有自己的开始／恢复与 closeout 入口，是可选接入方。

Kimi K3.1 Pro 已确认至少有“周期维护”和“交付对账／报告”两个独立结果。进一步按入口与独立上线价值细分为以下三项：手动周期管理可单独使用；普通开发自动接入让同一能力在开发过程中持续生效；周期报告提供跨周的完整结果视图。三项必需结果均可在 my-skills 交付；可选 pipeline 适配不强塞入其中的合入单位。

## 首个 MMF 的最小完整路径

**入口与参与者：** 开发负责人明确一个 Linear 团队／项目范围，通过 delivery-cycle 的周期维护动作取得并维护本周工作集合。

**范围收缩：** 首片选择一个获授权的验证范围；不先批量修改整个 workspace，不要求先接入所有 transport，不以周报或自动触发是否完成作为本片交付条件。

**完整路径：** 读取真实周期与进行中父子 Issue → 读取显式剔除与原交付证据 → 形成必要的归属／结转变更 → 在已授权范围内执行并读回 → 返回已完成变更和具体失败／Unknown。

**要验证的未知：** 主要验证技术贯通与交付能力。业务需求已在会话确认，不再做偏好访谈。配置与写入能力先只读核对；需要真实写验收时明确目标与授权，使用最小范围。假数据只能验证其覆盖的判断，不能冒充平台写入成功。

**验收证据：** 原 Issue／Cycle 标识、操作前后实际归属、Spec 与 main 证据来源、重复运行后的副作用变化及失败记录。至少拒绝下列错误实现：

- 因预计做不完而排除正在开发的 MMF。
- 用三张 Done ticket 冒充三个正式交付，或用 Integration 冒充 main。
- 用户剔除后自动加回。
- 跨周重新创建任务或重置原执行现场。
- 重复调用产生第二次写入成果，或写入失败却报告已同步。

## 依赖、并发与唯一 owner

依赖图：`M1 → M2`，`M1 → M3`；M2 与 M3 之间没有硬依赖。

共享 Interface 只暴露调用所需事实与承诺：原任务／MMF 身份、周期范围、显式排除选择、Spec 验收证据、真实 main 合入事实、正式交付判断、同步结果与失败原因。字段和错误模式由 M1 Spec 定义；这里不预建 DTO、Adapter 框架或新状态数据库。

M1 拥有周期管理规则与正式交付判定，原项目继续拥有输入证据。M2 只负责把普通开发生命周期事实交给 M1；可选 pipeline 调用也消费同一 Interface。M3 只消费同一判定和证据。对“已交付／未交付／Unknown”不能出现第二套算法。

合同稳定后，M2 的自动调用接入和 M3 的截止／去重／表达可以在隔离写入范围内并发设计或实现；其端到端验收仍须使用 M1 的真实结果。M1 未通过时，不以 fake 判定接口声称 M2 或 M3 完整验收。my-skills 内的共享文件重叠是合入协调风险，不额外制造业务阻塞边。

### M2 的普通开发触发覆盖

- **开始：** 普通需求进入 implement 等既有开发入口，已有真实 Issue／MMF 身份时维护归属。
- **恢复：** 按既有接手入口恢复原任务时重新核对本周，跨周维护不能重启开发。
- **本地合入：** git-rebase-main 完成本地 main 包含目标提交及必要验证的读回后，核对正式交付。
- **PR 合入：** gh-merge-pr 完成真实合入及目标分支 parity 读回后，核对正式交付。仅 Review、等待检查或进入 merge queue 不算合入。
- **重复与缺口：** 多入口可能到达同一事实，仍只调用同一 owner 并保持幂等。缺少目标平台或原任务身份时明确未同步，不伪造任务、不强制用户启用 pipeline。

本片修改的是 Skill 开发流程的实际入口，不引入通用 Git hook、文件监控或后台守护。绕过这些入口的外部工具不能凭 Skill 文案宣称已自动接入，需单独识别调用能力。

### 可选：delivery-pipeline 接入

用户使用 delivery-pipeline 时，可在其 canonical 开始／恢复与 main closeout 读回位置引用同一周期 Interface。该适配可独立规划、单独合入 delivery-pipeline 仓库；不会成为 M1、普通开发 M2 或 M3 的前置。未选择此适配时，三项必需结果仍须可完整使用。
