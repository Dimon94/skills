# To Epic

把对话、大需求或已有 Epic 整理成整体目标和一组 MMF 候选。MMF 是验收、合入与上线的单位，一个 MMF 对应一份 Spec、一个 MR；每个候选之后由 `to-spec` 写成一份 Spec。产品源码保持只读，本 Skill 交付规划和交接材料。

## 1. 读取上下文

读取目标项目的 instructions、术语、相关代码、现有 Interface、验收入口与 ADR。输入含 Epic 或需求引用时，读取正文、相关评论和已有 Spec，复用原坐标。

拆分前，按运行时目录定位并完整读取 `codebase-design/SKILL.md`，沿用 Module、Interface、Implementation、Depth、Seam、Adapter、Leverage、Locality 的定义。依赖缺失时点名路径和受影响决定，保留为未就绪。

写清用户结果、范围、不变量和已有决定。代码事实不清时用 `investigate`，外部约束不清时用 `research`，可行性需要实测时用 `prototype` 并在临时隔离目录运行；只处理会改变当前拆分或交付的未知。需要用户裁决的目标、业务语义或范围取舍，给出推荐再询问。

**完成条件：** 整体目标和约束可核对，关键事实有来源，未知有影响范围。需求按第 3 步的切分测试切不开、正好是一个 MMF 时，按第 5 步的交接写法请用户运行 `/to-spec`，本 Skill 到此结束。

## 2. 选首个 MMF

从用户主线里选择核心、小、能验证关键未知的一条完整路径。缩用户群、数据范围、规则或格式，使这个 MMF 能完整验收，并切不出两个各自能单独上线且有人用的部分。

写清谁从哪个入口做什么、得到什么结果，以及验收证据。分别说明要验证用户需求、技术贯通还是交付能力；已有可靠答案时直接做最小完整交付。能由更小探针回答的可行性问题先探测，探针产物单独标明。

对本片开放的行为，保留金额、授权、数据等实际不变量；验证规模与当前暴露面相称。

**完成条件：** 首个 MMF 有完整用户结果、明确验收和选择理由；阻止它成立的未知已有具体问题与解除条件。

## 3. 展开后续候选

沿用户活动、业务规则、路径、数据或输入方式逐步加厚。每个候选指回 Epic 的目标，并过两条切分测试：

- 上限：存在一种切法让每半都能单独上线且单独有人用，就拆成两个 MMF；切不开就是一个 MMF，不论大小。
- 下限：整体自己上不了线的部分不足一个 MMF，并进用到它的 MMF 作为 ticket。

多个 MMF 共用的使能工作（如一次数据库迁移）单独上线没人用，放进第一个用到它的 MMF，作为结构票，并写明服务的业务结果、保持的不变量与完成条件。

按 `codebase-design` 检查当前及准备并发的候选：相关 Module 的职责和状态 owner 清楚，复杂度收敛在拥有它的 Module，小而完整的 Interface 提供能力，主要行为测试与调用方穿过相同 Seam。优先复用已有 Module 和 Interface。

MMF 与 Module 不要求一一对应。远期候选保留结果、依赖和未知，临近执行再细化。

**完成条件：** 每项已批准结果都有候选或已有能力承接；每个候选写明两条切分测试的答案与依据；延后或取消有明确范围决定；每个当前候选有可核对的验收，远期未知保持可见。

## 4. 明确依赖与并发

每条阻塞边写清依赖的 Interface、能力或必须先取得的反馈，指出提供者和解除证据：

- 所需 Interface、数据、权限或迁移状态尚未可用，记录实际就绪条件。
- 首个 MMF 的关键反馈可能改变候选的范围、业务口径或验收，写明观察结果会改变哪个决定，只等待受影响部分。
- 普通文件重叠记录为冲突风险；共同状态、不变量或顺序约束按实际影响连边。

共享 Interface 对齐、写入可隔离时，可以并发推进 Implementation。真实能力依赖仍约束验收交付，受控 fake 或样例的证据只覆盖其实际验证范围。远期设计按需细化。

**完成条件：** 每条边有具体前提与解除证据；可并发候选有依据，受阻候选有等待点，独立部分可以继续。

## 5. 保存、交接与续接

向用户展示整体目标、范围与不变量、首个 MMF 及后续候选表、待决定事项；复用仍适用的确认。首次确定目标与拆分时取得确认；获批范围内自主细化、合并或拆分尚未开工的候选、更新依赖，报告实质变化。

新增、删除或改变已批准结果与验收、关键业务语义取舍、超出现有授权的成本或不可逆影响，交用户决定。已开工 MMF 受影响时先协调对应工作与 Interface，再更新候选和依赖。

按目标项目的 tracker 约定保存或发布，使用既有授权。未配置位置或未获发布授权时交付可审阅草稿，注明未发布。已有 Epic 定向更新，保留原 Spec 链接；写入后读回正文、关系与链接，部分失败报告实际成功坐标和剩余动作。

交接：`to-spec` 只能由用户调用。停下，请用户对当前就绪的候选运行 `/to-spec`，并列出 Epic、代码基线、范围、验收、相关 Module/Interface、前置条件和已有确认的指针，让 `to-spec` 不必重认。Spec 由 `to-spec` 拥有，生成后在 Epic 回链。这些产物可由任意符合目标项目约定的执行方消费。

**完成条件：** 规划产物可读回或明确未发布；当前可推进候选、等待点和交接输入齐全。规划完成、首个 MMF 完成与 Epic 全部结果验收分别报告。

## Epic 产物

正文保留目标、范围与不变量、候选表和待决定事项；已有代码、Spec、验收证据和决定用链接引用。

| MMF 候选 | 用户结果与验收 | 切分依据（切不开 · 整体单独上线有人用） | 相关 Module / 共享 Interface | 前置与解除证据 | 下一动作 / Spec 链接 |
| --- | --- | --- | --- | --- | --- |

续接时先读已有 Epic、Spec 和新反馈，核对变化，只重切受影响候选。整个 Epic 的交付完成由所有已批准结果的实际验收证明。
