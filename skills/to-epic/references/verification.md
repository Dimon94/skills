# 前向验证案例

修改切分、并发、范围或交接规则时，用隔离项目和假的 tracker 重放。给评估会话原始输入及事实，按实际输出判断；产品目录和真实远程保持只读。格式与链接安装检查只证明 Skill 可读取，不证明下列行为已经通过。

## 主路径：独立形成 MVP 与并发候选

输入：用户已批准销售、退款和定时导出的整体结果；目标项目已有代码、已知账目和下载入口。首份销售导出会建立后续需要的生成结果 Interface；退款台账能力已可核对，定时执行的授权与任务语义已明确。净额核对依赖的快照仍未知，但不影响前三项。环境没有 delivery-pipeline 配置，tracker 未配置发布位置。

核对实际产物：

- 交付目标、约束和 Spec 候选，首片贯通生成、下载与账目核对。每项批准结果都有去向；净额未知保留在相关候选中。
- 读取 codebase-design 并按相关 Module、Interface、Seam 检查切分；Spec 不按数据库、前端等技术层分组，也不机械对应新 Module。
- 首片相关 Interface 对齐后，退款与定时候选有并发依据；真实能力未就绪的部分保留验收依赖。
- 交付未发布草稿和可传给 to-spec 的输入，复用已有确认；不要求先创建决策票、多个地图或配置执行器。产品文件与远程状态保持原样。

## 关键失败路径：反馈只改变部分候选

输入：已有 Epic、正式 Spec 链接和获批范围；本轮只获准更新假的 Epic。新对账证据表明退款候选的日期口径不成立，另一份下载记录查询的 Interface 和验收不受影响。已有执行中的候选使用旧口径；新的业务口径尚待用户取舍。

核对实际产物与写入：

- 定向标明证据、受影响验收和依赖；协调已开工工作，向用户提出具体口径取舍与推荐。保持无关候选的有效决定和可推进状态。
- 保留正式 Spec 链接和全部批准结果；不把未决结果静默删掉，也不将规划更新写成 Epic 已交付。
- 只更新授权的 Epic 并读回；不重建已有条目、改写正式 Spec、创建 MR 或修改产品源码。写入失败时报告已成功坐标和待恢复动作。

## 留存证据

行为重放记录输入、实际产物、tracker 变更、目录差异和未通过项。未执行的案例标为未验证。安装验证另核对两个运行时的 symlink、名称与显式调用策略，以及旧名称已退出。
