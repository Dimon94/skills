# 修缺陷

交付的每一行都要能追溯到运行时证据。“可能有用”的加固只是假设，不交付。证据推翻一个假设时，回退由它引出的改动。只交付证据支持的最小改动。

1. 在缺陷发生的界面上自己复现：页面、CLI、agent 运行时，而不是邻近的单元测试。复现不出时，合成触发条件、收紧条件或加埋点，直到它出现。只有说得出具体原因、说明自己够不到目标时，才请用户复现。
2. 列出候选假设，用运行时证据逐个排除，直到只剩一个。用 `how` 看受影响的子系统，用 `why` 查回归历史。状态不清时加埋点读真实值，不猜。
3. 按 `principle-fix-root-causes` 在根因处修，并修掉同类位置。修复跨越函数边界时，先用 `how` 定落点。
4. 有便宜的本地检查时，按 `tdd` 的缺陷行先红后修；提交时，失败的复现排在修复之前。检查昂贵、重度集成或期望不清时跳过，并写明原因。
5. 在同一界面上验证：原来的复现现在通过。“不确定”或换了界面都不算通过，要明说。单元测试只说明分支行为，证明不了缺陷已经消失。同一复现在两次修复后仍不过时，按 `principle-attack-the-premise` 写下两次修复共同的前提并先验证它，再写下一个修复。
6. 用 `code-review` 审查：把复现与根因作为 spec 源、修复开始前的提交作为 fixed point 交给它。

回复写四段：坏了什么、根因、修复、怎么验证的。原样粘贴先失败后通过的复现输出。
