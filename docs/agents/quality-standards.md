# Quality Standards

用途：新增、修改或删除测试，以及代码审查、重构和交付前自检。

## 1. 报告顺序

1. Scope。枚举相关审查范围，按用户影响和风险排定优先级。
2. Findings。按严重度排序。
3. Coding。检查局部正确性、类型、错误、测试和坏味道。
4. Architecture。检查所有权、依赖、interface 和持久状态。
5. Spec。独立核对需求和验收标准。
6. Verification gaps。记录未运行测试、未覆盖路径和剩余风险。

每个 finding 必须包含：

- 具体文件和行号。
- 可触发场景。
- 可观察影响。
- 证据。
- 最小修复方向。

没有证据时写 Unknown，不报告为缺陷。工具已覆盖的通用或表面发现省略不报。

交付阶段决定 finding 的处理路径，不决定是否报告。根 repo://AGENTS.md `<stage>` 判定为延后的加固类 finding 照常出现在报告里，并登记进 repo://docs/deferred-hardening.md。

## 2. 严重度

- P0：正在造成不可逆数据损坏、严重安全问题或全面不可用。
- P1：主路径必然失败、权限绕过、持久状态污染或外部合同破坏。
- P2：特定条件下错误、恢复失败、明显性能回归或高扩散维护风险。
- P3：局部清晰度或一致性问题，当前不破坏行为。

严重度由影响和可触发性决定，不由规则名称决定。

## 3. 正确性

检查：

- 输入边界是否完整。
- 状态和身份是否由正确 owner 校验。
- 成功条件是否断言业务 outcome。
- 失败是否显式且可恢复。
- 并发、重试和幂等是否保持不变量。
- 持久写入是否原子且可读回。
- 外部副作用是否可能重复。

## 4. 简洁性

应用：

- KISS：选择满足需求的最简单方案。
- YAGNI：删除当前需求不使用的扩展点。
- DRY：消除重复规则，不抽象偶然相似语法。
- SOLID：作为诊断工具，不作为增加层级的许可。

每个新增实体都要通过必要性检查。每个可疑模块都要通过 deletion test。

## 5. 坏味道

坏味道清单归 repo://docs/agents/coding-standards.md 第 11 节（局部）与 repo://docs/agents/architecture-standards.md 第 11 节（结构）。静默兜底的判定归 coding-standards 第 6 节 fail-close 规则。

发现坏味道时说明当前影响。不要把审美偏好写成 finding。

## 6. 测试质量

- 测试只服务当前改动的验收：不补历史覆盖率，不铺未来测试体系，不引入新测试框架或基础设施。代码发生变化或覆盖率上升不能单独证明测试必要。
- 只为现实可观察回归、非琐碎不变量或边界，以及具体缺陷新增测试。新增前回答三问：它验证哪个已被接受的需求？去掉它，现有测试是否就无法发现这次回归？它是否比实现本身更复杂？
- 默认上限：本次改动的 1 个主路径，必要时再加 1 个关键失败路径。测试比实现更长或更绕视为过度工程，缩测试或缩实现。
- 优先扩展行为边界上的现有覆盖。
- 测试不镜像字面量、映射、显然控制流或实现细节；已删除能力仅在“不存在”本身是合同时保留测试。
- 并发测试优先使用确定性协调或受控调度；固定 sleep 只作为无法消除的外部时序边界，并记录剩余不确定性。
- 检查错误实现是否会失败。
- 检查是否穿过 public interface。
- 检查断言是否关注结果和不变量。
- 检查 mock 是否隐藏真实合同。
- 检查 fixture 是否可能访问真实外部系统。
- 检查时间、随机和并发是否可重复。
- 检查是否缺少关键负向路径。
- 断言用户可见输出前先展平空白（`" ".join(output.split())`）：测试运行器的控制台约按 80 列换行，多词子串会被切断。清除 FORCE_COLOR/COLORTERM，防止 ANSI 进入捕获输出。机器可读格式同时断言必须不存在的内容。
- 测试代码的注释和公开 API 文档遵循 repo://docs/agents/coding-standards.md 第 8 节。

## 7. 完成条件

测试变更只有在第 6 节所有命中规则均已应用，且每个新增或修改测试会在目标错误实现下失败时完成。

Review 只有在以下条件成立时完成：

- 当前 diff 每个语义边界已检查。
- Coding 和 Architecture 两轴均已覆盖。
- Spec 独立核对。
- 每个 finding 可由证据复现。
- 无 finding 时仍列出验证缺口和剩余风险。
