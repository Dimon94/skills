# 按票委派

技术负责人输入原票号、票面、引用的 Spec 场景和目标仓库。交付一组 `Brief`，或带原票号的 `MissingDecision`。字段见[交接合同](../to-tickets/references/delivery-contract.md)。

1. 在目标仓库用 `git rev-parse HEAD` 取得确定基线，读票面的 Kind、Owns、Respects、Interface、Ensures 和边界。按规划侧的单票规则核对 Kind 与 Owns，归属冲突交拆票者在原票上修正。读 `Blocked by`。依赖为 Unknown 时沿原票号交回拆票者。依赖已命名时，逐票读回完成证据，把票号和已落地的交付提交填入 `site.dependencies`，派发基线须包含这些提交。在该基线上查现有入口、先例和可运行的检查。逐项对照原场景的前提、动作、全部结果与独立预期。票面只剩“停止成功”、原场景还要求“第一段仍可读”时，把遗漏的结果、原场景和决定者写入 `site.decisions`。技术负责人补现场，拆票者补责任，需求作者裁决业务冲突。沿原票号重跑。
2. 默认写一份草案。只有各片能独立验证且写入互不重叠时才拆。每片写清可直接实施的设计、签名与承诺、归属、获准文件、基线上要先读的相对路径、一条验收命令、该命令的具体预期和排除项。金额、权限、去重、并发等命中项目门禁的规则点名检查和负责片。先集中完成共享改动，再从新基线准备依赖它的下一波。按每条 T/R 和每项结果核对各片合起来覆盖原票，编号相同仍要核对语义。
3. 在目标仓库根，将 `{ticket, scenarios, base, site: {slices, decisions, dependencies}}` 作为 JSON 从标准输入传给 `node <本 Skill>/scripts/prepare.js`。`slices` 是上一步写出的草案，字段见合同 `Site`，脚本绑定父票和基线。`decisions` 为空数组时表示已完成语义对账且无缺项。退出 1 时把具体缺项交给该 owner。退出 0 时保留**完整合同清单**供核收，交付每份合同。
4. 用户已授权委派时，通过宿主实际启动开发者，在各自从合同基线建立的独立工作树中运行 `implement` 的派发合同入口。每人只收到本片合同、必要项目约定及其指针。收回每人的 `SliceEvidence`，按原清单的 `ticket + slice_id` 核对基线、提交、命令、观察和缺口。缺片继续收，缺证交原开发者补。同一票收齐后交 MMF 负责人在集成提交按原场景验收。人工转交时直接给出合同和回执格式；Driver 模式把合同或回执交还 transport，由宿主启动与回收。
