# 环境改动的放置规则

## 实现与审查

所有工作都经过两个阶段：实现和审查。实现 agent 的上下文压力最大：探索、写代码、调试失败都归它。审查 agent 的压力最小：它拿到 diff，不用探索，通常不用写代码或调试。

所以编码规范由审查 agent 执行，不压给实现 agent。审查 agent 漏掉错误时，改审查规则或加检查，不往实现侧的常驻指令里加规则。

## 自动检查

- 先读项目自己的检查命令：`package.json` 或构建工具的 lint、check 脚本，CI workflow。已有却没接线、或已悄悄坏掉的检查本身就是发现，不重新发明。
- 仓库没有任何防护（没有 pre-commit hook，也没有跑 lint、类型检查或测试的 CI job），本身就是一条发现：没有 lint 的仓库是一个持续错过的机会，不是中性的默认。
- 机械性违规按项目语言和既有防护，选最便宜的一种：项目 linter 里的自定义规则、新的 pre-commit hook，或新的 CI job。默认建检查，不写规则。

## 文件

- `AGENTS.md` / `CLAUDE.md`：会被推进每个在本仓工作的 agent 的上下文。极少量使用，通常只放指向其他文件的导航指针。过大时，把转向指令移到编码规范或自动检查。
- 编码规范文档（如 `CODING_STANDARDS.md`）：审查时读，实现时不读。超过 1000 行时，加指向 docs 目录的导航指针。
- docs：当参考文件，由其他文件指向。新写之前先找已有的。
- Skill：适合做“文档”，因为它的 description 会进入 agent 上下文；也适合做用户调用的命令。
