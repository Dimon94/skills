# 注释除草

只在用户显式调用时执行。范围取用户指定的文件或 diff；未指定时取相对 base branch 的当前 diff，默认 `main`，包含暂存与工作区改动。空 diff 则报告无可审查内容。读取邻近代码取证，不扩大写入范围。

## 步骤

1. 读取 [Comment Sicko 审查规则](references/comment-sicko.md)。宿主支持子 agent 时，派一个只读审查者，传入规则、范围和目标项目规范；使用宿主原生接口，不依赖预注册的 `comment-sicko` agent 类型。宿主没有子 agent 时，自己按同一规则审查，并披露缺少独立视角。
2. 复核每项删除、保留和根因修复建议。拒绝越界结论、没有代码坐标的断言和误删例外；审查者修改了文件则拒收。对 `IMPORTANT`、`do not remove`、抑制规则和绕路理由，追到具体符号，必要时调用 how 或 why。证据不足标为 Unknown，保留待查；不能把改短注释当修复。拒收后带原因重审一次；再次拒收则明确失败，不应用该报告。
3. 删除已确认无用的注释。对自身代码的特殊情况，先问：删掉死路径、参数或绕路，改用真实 API、清晰命名、类型或更简单结构，能否让解释不再需要？需要结构变化时先给最小草图，再在授权范围内修复根因。根因在范围外则报告具体坐标与未解决项，不叠加症状守卫。
4. `do not remove`、固定措辞等约束若能由类型、运行时校验、测试或 lint 表达，提出成本最低的编码方案。已有授权覆盖时直接实现；否则等待批准，期间保留尚未编码的有效约束。外部平台怪癖等必要注释继续保留。删除正确性或安全性抑制前，先修复它压住的问题，并运行相应检查；验证不了就保留并报告阻塞。
5. 运行目标项目相关的最小验证，检查 diff 只包含范围内已接受的改动。报告删除数、保留理由、根因修复、恢复项、重审次数、约束编码和 Unknown。无法验证的行为不能宣称已修复。调用本 Skill 不授予提交、推送或发布权限。
