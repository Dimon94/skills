# Test Review

只读审查测试及其证明的行为。Standards 判断是否遵循项目测试规范；Spec 判断是否保护已接受需求。相关生产代码、调用方和 CI 用于核实测试证据，不扩展为全仓代码审计。

## 1. 固定范围

记录仓库、固定点、目标 HEAD、工作区状态和请求范围。用户或 caller 提供了 Review Packet / Evidence Bundle 时，核对并复用其精确 base、head、diff 关系和路径清单。未提供固定点且无法从明确的 PR/MR 坐标取得时，只补问该缺口。

分支比较使用解析到提交的固定点与目标 head：记录 `git merge-base <base-sha> <head-sha>`、`git diff <base-sha>...<head-sha>` 和 `git log <base-sha>..<head-sha> --oneline`。caller 要求精确两点比较时沿用其关系，不换成 merge-base。先核对 ref 有效、范围非空，再分派审查。

WIP 包含请求范围内的 staged、unstaged 和 untracked 文件；分别保存内容与路径，不让 HEAD diff 漏掉未提交测试。存在其他写者或无关 dirty 时，由 caller 提供隔离快照。两轴读取同一版本；审查后核对 head 与工作区输入，变化使原结论失效。

枚举新增、修改、删除的测试、共享装置、测试配置和 CI 入口；沿测试导入和被测入口补读相关实现。生产行为变更但没有改测试时，仍核对现有覆盖。空范围报告“无待审改动”；没有测试改动不等于测试正确。

完成条件：两轴有同一份固定证据；高价值行为有待检查的测试坐标或明确缺口，其余行为有覆盖取舍。

## 2. 加载项目依据

先读目标仓库的根级与最近 `AGENTS.md`，按其导航查测试原则、质量规范、验证流程和模块测试入口。存在 `CODING_STANDARDS.md`、`CONTRIBUTING.md` 时列入规范来源；常见落点包括 `docs/agents/quality-standards.md` 的测试章节、`coding-standards.md`、`ui-e2e.md` 和 `ci-demand.md`，只读取当前命中的部分。

从 manifest、测试配置、pre-commit 和 CI 读取真实发现命令、选择规则和失败传播。区分“文档要求”“已接线”“本次实际运行”；已有检查漏接或失效时，问题是接线，不另造相同规则。

Spec 优先使用用户指定的 issue / spec / 验收标准，再按提交或 PR/MR 引用查 originating spec；平台读取遵循目标项目的 issue-tracker 指南。找不到时询问来源，同时继续 Standards；用户确认没有 Spec 或来源不可读时，Spec 标记 Unknown / 未审，不以当前实现或测试期望值充当需求。

项目规范优先于下节的通用审查问题。没有规范时标记“无项目测试规范”，只作有行为证据的判断，不把本 Skill 的经验写成项目硬规则。

### 二八原则：先选高价值测试

测试覆盖以少量关键测试保护主要业务价值：聚焦约 20% 能产生约 80% 价值的测试，其余低价值内容允许少覆盖或不覆盖。比例用于取舍，不是测试数量或代码覆盖率配额；没有证据时不编造价值比例。

- 先按已接受需求、真实使用频率、失败损失和已发生回归选出最小关键测试集。优先核心主路径和关键失败边界；本次命中的金额、权限、数据损坏或历史丢失风险即使低频，也属于高价值。
- 补测必须说明新增的高价值保护，以及现有测试为何不足。重复场景、实现细节和低影响组合穷举优先缩减；不因改了代码就要求每个分支都有测试。
- 低价值未覆盖只记录取舍与剩余影响，不自动判成漏测、FAIL 或 Unknown。已接受验收和项目强制检查仍须满足；证据不足以判断价值时，写 Unknown，不冒充低价值。

审查测试价值或删测覆盖时，必须读 [测试启发式](references/test-heuristics.md)：业务结果、独立预期、消融测试与关键词排查。两轴分别取得该文件；用其定位疑点，再按项目规范与 Spec 核实。

完成条件：列出适用规则的文件与章节、Spec 来源、最小关键测试集和实际验证入口；必要来源缺失各自标明 Unknown。

## 3. 分别审查两轴

宿主支持子 agent 时，由 coordinator 启动两个独立只读审查者。分别给出固定坐标、完整路径与提交清单、规范来源、Spec 来源及本节对应轴的要求；允许读取相关实现，但不传递另一轴的结论。单轴审查者只返回本轴，不再次分派两轴。只有 coordinator 执行需要写临时状态的测试；两轴复用其证据。宿主不支持并行时分两轮独立审查，报告执行方式。

### Standards：测试机制与必要性

先检查关键测试的判别力与执行成本，再核对低价值场景能否缩减。按二八原则选定的场景核对项目规则、局部断言、装置所有权、隔离和执行接线：

| 检查面 | 必须回答的问题 |
| --- | --- |
| 判别力与独立预期 | 哪个具体错误实现会使断言失败？预期来自哪份独立依据？断言是否执行真实被测入口并观察业务结果、错误或副作用？等价重构为何应改变结果？ |
| 替身边界 | 被测 owner 是否仍执行真实逻辑？替身是否只替换必要的外部 seam？假摘要、假连接池或假状态机是否遮住本次要证明的行为？ |
| 装置与隔离 | 数据、账号、迁移、服务和等待是否对应本例的角色或失败方式？复用模板后每例可写状态是否独立，并正确清理？时间、随机和并发是否可复跑？ |
| 重复与失效 | 与现有场景是否保护同一输入、动作和错误？旧合同是否真的退役？保留、合并或删除建议是否给出具体覆盖坐标？ |
| 执行与成本 | 测试是否被实际发现并接入本地/CI？重试、skip、超时和 allow-failure 是否掩盖失败？选择器是否覆盖调用方、公共输入、删除/重命名，并把子流水线失败向上传播？ |

按启发式中的关键词查找候选，沿实际值、预期值与被测入口追踪其来源。合法使用场景与风险信号一起核对；关键词命中本身不是 finding。慢测试若保护独有的高价值边界，优先减少装置成本；只有低价值保护的测试可提出缩减，不能仅凭耗时或覆盖率决定。

对删除或合并建议，列出被替代场景的入口与断言，核对替代覆盖；没有替代覆盖时，说明为何可接受失去这项低价值保护及其影响。唯一高价值覆盖应保留，存在独有覆盖本身不构成保留全部测试的理由。通过的 lint 不代替业务审查；工具已经可靠报告的表面问题只引用检查结果，不重复制造人工 finding。

新增测试与删测候选先静态核对独有保护；高价值保护或替代覆盖有争议时，才做最小“消融测试”。不能证明保护变化时写 Unknown，不为每条测试追加消融运行。AI 生成成本低不替代业务价值、CI 与维护成本判断。

### Spec：业务证明是否成立

将本次受影响的高价值需求与明确要求的验收逐项映射到受益角色与业务结果、Given 前置状态、When 真实动作/入口、Then 可观察断言和现有覆盖。其余需求说明少覆盖或不覆盖的理由；GWT 用于澄清关键场景，不要求改写全部测试语法：

- 测试期望是否符合需求，而非把错误实现钉成合同？主路径与实际命中的失败边界是否有判别力？
- 删除或弱化断言后，哪种具体回归会漏过？命中权限隔离、支付幂等、历史保留、配额结算、升级/回填/回滚或恢复时，核对相关旧数据与状态，不预建未涉及的测试体系。
- 新增测试是否保护本次需求，还是重复当前常量、已退役行为或未要求的功能？生产行为变更能否被已有测试实际发现？
- 证据是否穿过约定入口并读回真实结果？HTTP 成功、全绿、覆盖率、截图、mock 响应或 CI 完成各能证明哪一层，仍缺哪一层？

每条缺口给出需求坐标与可触发反例；缺少依据时列为 Unknown，避免把猜测需求报告成漏测。

完成条件：两轴检查高价值边界与明确验收，说明其余边界的覆盖取舍；每个 finding 都有具体触发、影响、代码坐标和独立依据。

## 4. 最小验证

先读已有执行记录，核对 SHA、输入范围与结果。先解决关键测试中的失败和具体疑问，再决定是否扩大运行；不默认重跑低价值长尾或整套测试。需要验证时，从项目已有命令选择能排除具体疑问的最小检查，项目强制检查照常执行；记录命令、退出结果和日志/报告坐标。缺陷可在隔离临时副本验证一个具体错误实现是否被测试拒绝；静态推断与实际反例运行分别报告。无需全量 mutation、覆盖率工程或真实付费/生产操作。

审查范围保持只读：不修改被审代码、规范、Git 历史或外部系统；临时反例在隔离副本执行。测试运行会接触外部服务或共享可写状态时，先满足项目隔离与授权要求。无法执行时继续静态审查，点名验证缺口。

只有运行范围、环境和缓存条件可比时才比较成本；执行时间、排队与并行链路墙钟分别记录。数据不足时提速比例为 Unknown。

完成条件：已解决疑问有对应证据，未解决项和未运行原因可读回；必要检查通过后停止扩大验证。

## 5. 输出

先给 Scope：base/head、diff 关系、WIP 范围、规范/Spec 来源和验证入口。

coordinator 分别使用 `## Standards` 与 `## Spec`；单轴审查者只提交对应轴。各轴内部按项目严重度排序；无项目分级时按可触发影响排列。每条 finding 包含文件与行号、场景、可观察影响、规则或需求坐标、代码/运行证据和最小处理方向。经验性判断标为“判断”，静态因果标为“推断”，证据不足写 Unknown。区分本次引入问题与既有问题。

每轴单独报告 finding 数、最严重问题与结论：已确认阻断问题为 FAIL；必要来源或验证不足为 Unknown；其余按项目门禁报告，注明仅静态审查或已运行范围。两轴不合并、不跨轴重排，重复关注同一处时各自保留依据。

用紧凑列表给出关键保留、合并/删除候选和允许少覆盖或不覆盖的内容，列出独有保护、替代覆盖或接受损失的理由。说明哪些测试承担主要价值，哪些成本可省；不以测试数量或覆盖率高低作为结论。最后列出未运行的必要检查和剩余风险，区分关键缺口与主动接受的低价值取舍。规则或机械门禁建议交回项目 owner；本 Skill 不自动改规范、删测试或批准合并。
