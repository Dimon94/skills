# 修缺陷

交付的每一行都要能追溯到运行时证据。“可能有用”的加固只是假设，不交付。证据推翻一个假设时，回退由它引出的改动。只交付证据支持的最小改动。

1. 按 `mattpocock-skills:diagnosing-bugs` 的 Phase 1–4 建反馈回路、复现并最小化、排假设、加埋点。回路打在缺陷发生的界面上：页面、CLI、agent 运行时，而不是邻近的单元测试。只有说得出具体原因、说明自己够不到目标时，才请用户复现。
2. 排假设时用 `how` 看受影响的子系统，用 `why` 查回归历史。用运行时证据逐个排除，直到只剩一个。
3. 按 `principle-fix-root-causes` 在根因处修，并修掉同类位置。修复跨越函数边界时，先用 `how` 定落点，再用 `architect` 定形状。
4. 按 `bdd` 在原公开入口用同一输入先复现，再修复。能证明原症状的既有检查可直接复用。入口不可用时记录原因与缺口。
5. 在同一界面上验证：原来的复现现在通过。同一界面包括用户截图里的默认状态（折叠、未展开、首屏），不先展开或切换再验。改动只收窄一部分行为时，同时验证被保留的那部分仍然生效。“不确定”或换了界面都不算通过，要明说。单元测试只说明分支行为，证明不了缺陷已经消失。同一复现在两次修复后仍不过时，按 `principle-attack-the-premise` 写下两次修复共同的前提并先验证它，再写下一个修复。
6. 不单独调用 `code-review`：第 4、5 步先失败后通过的复现就是验证。修复属于进行中的 MMF 时，由 MMF 收口的那一轮审查覆盖。

回复写四段：坏了什么、根因、修复、怎么验证的。原样粘贴先失败后通过的复现输出。
