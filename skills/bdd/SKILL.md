# 用业务场景决定怎样验证

1. **写出能区分对错的场景。** Given 谁处于什么状态、已有何种数据；When 谁从哪个公开入口执行什么动作；Then 能读回哪些结果或外部副作用。逐项写出结果和动作后的不变量。每个预期注明独立来源：已批准的 Spec、用户确认的具体例子、真实缺陷复现、手算结果、外部标准，纯重构用旧版本行为（特征测试）。预期只取自这些来源。
2. **用变异体检验已有检查。** 对照项目测试规范，读已有检查的输入、入口和断言。设想一个会让用户拿到错误结果的变异体，判断这条检查能否杀死它。只做交互断言的检查杀不死「调用了但结果错」的变异体，要补状态读回。单一规则在最快的公开 Seam 检查，跨组件接线从公开入口读回。金额、权限、并发与去重规则须杀死相应的变异体；时序组合优先用项目已有的有界模型检查。结构调整沿同一公开入口对照旧版本行为。
3. **逐场景交回决定和理由。**
   - **复用**已有检查。给出检查坐标、它杀死的变异体和已覆盖的结果；同一条检查可以覆盖转移及其不变量。
   - **新增或补强**检查。点名既有证据杀不死的变异体，只补缺口。缺陷先做最小复现，让检查失败，再用同一检查验证修复。已确定的新行为可先写失败检查，再实现并重跑。
   - **待裁决**。列出尚不明确的结果、冲突来源或未确定的公开入口，由需求作者补齐业务决定，技术负责人补现场。保留原场景和票号。

例如，用户在回合详情看到「第一段」后点击停止，回合应显示已停止，详情仍能读到「第一段」。能从详情读回这两个结果的检查直接复用。若检查只断言停止函数收到调用，「清空结果」的变异体也能通过，应补详情的状态读回。若用户尚未决定停止后如何处理已有结果，把这项决定交回需求作者。

写 Spec 时，把确定的例子写入 [Testing Decisions 的场景表](../to-tickets/references/delivery-contract.md)。开发者沿派发合同提供的场景执行聚焦检查，技术负责人在集成版本按原场景核对整体验收。
