# Entropy Governance

用途：发现重复模式、并行机制或新增抽象时，寻找最近的正确机制。

## 1. 先找现有范式

写代码前按 repo://docs/agents/coding-standards.md 第 2 节的复用顺序与搜索键寻找现有机制。

找到现有 owner 时，扩展它。复用会破坏 ownership 或 locality 时，记录不适用理由。

## 2. 只保留一个机制

同一语义只保留：

- 一个 canonical type/schema owner。
- 一套错误语义。
- 一个日志入口。
- 一套 HTTP 或外部请求封装。
- 一套状态管理方式。
- 一个持久写入 owner。
- 一个测试入口。

修改既有规则优先于在旁边新增规则。与被替代规则并存的新常量、flag 或分支会形成两个真相源，需要推理的状态数翻倍。

替换旧设计执行 clean-break：同一次变更彻底切换到新机制并删除旧路径，不留 legacy path、deprecated alias 或新旧并存分支。

兼容是成本，必须已有人在付。迁移路径、双读和 deprecated alias 只在真实用户持有旧状态时存在；无存量用户时 clean-break 是更小变更。这是事实问题，不是谨慎问题。

迁移期需要双轨时，明确 canonical 路径、临时路径、切换条件和删除时间点。

## 3. 抽象门

新增抽象必须同时满足：

1. 当前存在至少两个真实 caller 或 adapter，或存在必须隔离的外部协议。
2. 抽象隐藏稳定复杂度。
3. 删除抽象会让规则散到多个 caller。
4. 名称来自 CONTEXT.md 或已确认工程词汇。
5. 测试能穿过其 public interface。

任一条件不成立时，保持直接实现。

## 4. 删除优先

处理重复时优先：

1. 删除废弃路径。
2. 让 caller 使用现有 owner。
3. 合并重复规则。
4. 删除无价值 wrapper。
5. 最后才新增共享抽象。

## 5. 验证

完成标准：

- 相同规则只有一个 owner。
- 新代码符合最近目录的现有模式。
- 没有新增平行错误、请求、状态或持久化机制。
- 被替换的旧机制已随本次变更删除，无新旧并存分支。
- 临时兼容路径有可检查的删除条件。
