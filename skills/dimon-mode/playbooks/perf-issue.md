# 修性能问题

每个修复都对应一次测量。读源码得不出性能结论，跑出来的数字才算。要对着一个指标反复优化时，改走 [`hillclimb.md`](hillclimb.md)；需要先在活进程取证走 [`runtime-forensics.md`](runtime-forensics.md)，已有现成 profile、堆快照或 trace 文件走 [`trace-forensics.md`](trace-forensics.md)。

1. 量基线。在用户觉得慢的那个界面上（页面、CLI、agent 运行时）测一次，写下目标数字；用户给了数字就用用户的。基线和之后的每个数字，都按运行时目录完整读取 `benchmark-checklist/SKILL.md` 逐问核对。完成条件：一条可重复的命令、一个带单位的基线数字、一个目标数字、产物路径。
2. 用 `how` 追受影响的代码，给每个假设找到依据；是回归时用 `why` 查历史。没跑过就不下“已到上限”的结论。按下面的顺序试，便宜的在前，前一条达标就停：
   1. 不做。没人用结果的工作直接停掉，不去把它做便宜。
   2. 做，但不做第二次。
   3. 少做。
   4. 晚点做。
   5. 趁用户不注意时做。
   6. 并发做。
   7. 做得更便宜。
3. 按测量结果定修法。修复跨越函数边界时，先用 `architect` 定形状。按 `principle-sequence-verifiable-units` 一次只做一个尝试，量完再做下一个。
4. 用第 1 步的同一条命令、在同一界面重测，和基线对比。“不确定”或换了界面都不算通过，要明说。完成条件：修后数字达到目标，或回复写明差多少、卡在哪。
5. 提交正文写基线、修后数字和产物路径。

回复写四项：基线数字、修后数字、差值、产物路径。
