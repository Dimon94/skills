# 周期呈现

让读者直接看懂本周解决什么需求、用户能得到什么，以及怎样算完成。适用于候选方案、Cycle 描述改写和周期结果汇报。

## 按需求组织

回源 Issue 的正文、原 Spec 和父子关系，把同一需求的执行票归到一个业务目标下。目标写「具体需求名称 → 用户可感知的变化 → 完成标准」。需求未核实时保留 Unknown，点名缺失信息。

正文以具体需求名称为主语。对话或关联文档需要追溯时，把 Issue 链接放在需求名称上，或单列关联任务；编号只承担定位作用。读者不点链接也应看懂目标。同一需求的多张 ticket 只说明一次业务目标；独立 Bug、研究保留各自类别，正式交付身份仍按 SKILL.md 核实。

## 对话展示

默认先给一张紧凑结构图，再给必要说明。简单目标用文本树；依赖或交付条件用 Mermaid；需要呈现卡片布局或较多需求时用一个聚焦 HTML，并通过当前环境的展示工具呈现。选其中足够说明问题的一种，避免重复展示。

最小结构：

```text
周期主题 · 起止日期
├─ 具体需求名称
│  ├─ 用户变化：谁现在能做什么
│  └─ 完成标准：可观察、可核对的结果
└─ 另一项具体需求
   ├─ 用户变化：谁现在能做什么
   └─ 完成标准：可观察、可核对的结果
```

候选方案标为计划目标；结果汇报依据证据标明已完成、进行中、阻塞或 Unknown。正式交付复用 SKILL.md「正式交付」判断，图示不另设公式。保留所需的部署与真实平台验收区别。

## Linear 描述

写成一段简短纯文本，优先用两三句讲清具体需求与预期结果。使用自然语句和标点；图示、Markdown、列表编号及箭头留在对话或关联文档。按实际字段长度限制精简，完整保存并读回，确保侧栏可读。

需求目标放在最前，维护、交付与周报只保留必要短句；详细规则仍归 SKILL.md。需要写周报时间时，使用下周一的绝对日期、08:00 和 Asia/Shanghai。目标措辞描述待达成结果，完成措辞须有证据。

完成：读者无需查编号就能解释每项业务目标；关联任务可追溯；计划与实际结果区分清楚。仅展示草稿不等于已写回 Linear，写回仍以保存后的完整读回为准。
