# Implement

实现用户在 spec、计划或 tickets 中描述的工作。小改动没有计划时，以用户的请求为 spec。

## 1. 读入验收

用户给了票号时，从 issue tracker 读取并先说出票标题；票号有歧义就问。

列出本次验收。每条验收要带独立预期：输入或动作、期望结果、来源（定义见 `tdd` 第 2 步）。spec 或计划里缺的，从原文补；指不出来源的，停下来问用户。

完成条件：每条验收都有独立预期，或已经交给用户确认。

## 2. 按切片实现

按 vertical slice 推进，每片调用 Skill `tdd`。常跑类型检查和单个测试文件。

完成条件：每条验收都走完 `tdd`，留下运行记录或不写测试的理由。

## 3. 真实运行

1. **E2E**：按改动影响选相关场景。影响面从调用方、共享 Interface 和项目的场景注册表判断，判断不清时用 `blast-radius`。大重构跑全部能跑的场景。被 skip 或因前置缺失未执行的场景不算通过，列为缺口。
2. **形式验证**：改动触及项目 `formal-verify-<area>` 覆盖记录里的文件或函数时，必须运行。核心链路上有测试难以穷举的承诺（并发、重试、幂等、状态机、资金、去重）且没有覆盖时，在交付说明里提议 `create-formal-verification-skill`，不在本次创建。
3. **全量测试**：结束前跑一次项目的完整测试命令。

完成条件：每项检查都有命令和结果；未跑的列出原因。

## 4. 审查

以本次工作开始前的提交为 fixed point，调用 Skill `code-review` 一次，按它的严重度处理 finding：

- **P0/P1**：修复，再按 `code-review` 的复审范围复核，直到没有未解决的 P0/P1。
- **P2**：先在项目 tracker 里查重，没有同类就发 issue，正文写触发场景、影响、证据坐标与修复方向。项目把这类问题归为阶段性延后加固时，按项目规则登记，不发 issue。本 Skill 授权这一步的远程写入。
- **P3**：留在报告里，不处理。

完成条件：两轴 verdict 都是 `PASS`；每条 P2 都有 issue 链接或登记位置。

## 5. 对账与提交

逐条核对：每条验收对应哪项检查、结果是什么。对不上的就是缺口，写进交付说明，不改写验收去迁就实现。

提交到当前分支。提交说明写：验证命令与结果、不写测试的理由、未跑的检查与剩余风险。

完成条件：交付说明里每条验收都有检查与结果，或列为缺口。
