# Implement

实现用户在 spec、计划或 tickets 中描述的工作。小改动没有计划时，以用户的请求为 spec。

## 1. 读入验收

用户给了票号时，从 issue tracker 读取并先说出票标题；票号有歧义就问。

从 spec 逐条拆验收：每个“必须”和“不得”都有一条。每条验收要带独立预期：输入或动作、期望结果、来源（定义见 `tdd` 第 2 步）。spec 或计划里缺的，从原文补；指不出来源的，停下来问用户。

按改动命中的情况，再列失败方式，它们也是验收：

- **异步写**：等待期间换身份或离开、迟到响应、取消、重入。
- **持久写**：部分失败、重启恢复、旧版本数据。
- **状态跨步骤，或有重试、取消、不可逆副作用**：对照 spec 的 Business Flow 状态图；没有就画一张，放进交付说明，让用户判断是否符合意图。

完成条件：spec 的每个“必须”和“不得”都有验收；每条验收都有独立预期，或已经交给用户确认；命中的失败方式已列出。

## 2. 按切片实现

动手前先做减法：按运行时目录完整读取 `principle-subtract-before-you-add/SKILL.md` 和 `principle-laziness-protocol/SKILL.md`，列出本次范围内可删的现有复杂度（死代码、spec 没要求的校验、空壳引用），先删再加。

按 vertical slice 推进，每片调用 Skill `tdd`。常跑类型检查和单个测试文件。

这一片不是一眼能看完的几处编辑时（批量修改、迁移、分析、验证），按运行时目录完整读取 `principle-build-the-lever/SKILL.md`，先写能重跑的脚本、codemod 或生成器，用它完成或证明这片工作。

完成条件：每条验收都走完 `tdd`，留下运行记录或不写测试的理由；已删项列出，没有可删项时写“无”并列出检查过的范围。

## 3. 真实运行

验证按层叠加：类型、lint 与 API 设计先排除一类错误，测试和真实运行证明行为，形式验证只给真正需要的部分。

1. **入口清单**：列出本次改动的 Interface 的全部调用方和公开入口，逐个确认接上了新合同，过期的断言和文档同步修改。
2. **E2E**：按入口清单和项目的场景注册表选相关场景，判断不清时用 `blast-radius`。大重构跑全部能跑的场景。被 skip 或因前置缺失未执行的场景不算通过，列为缺口。
3. **形式验证**：改动触及项目 `formal-verify-<area>` 覆盖记录里的文件或函数时，必须运行。模型检查报告的路径要在真实代码上复现，复现不了先怀疑模型。它只证明实现符合模型里的规则，规则是否符合意图由用户判断。核心链路上有测试难以穷举的承诺（并发、重试、幂等、状态机、资金、去重）且没有覆盖时，在交付说明里提议 `create-formal-verification-skill`，不在本次创建。
4. **全量测试**：结束前跑一次项目的完整测试命令。

完成条件：每项检查都有命令和结果，结果读自真产物（运行中的功能、实际值、diff）：按运行时目录完整读取 `principle-prove-it-works/SKILL.md`，编译通过、子代理自述、文件时间戳不单独算通过；入口清单已逐个确认；未跑的列出原因。

## 4. 对账

先做消融：按运行时目录完整读取 `principle-minimize-reader-load/SKILL.md`，逐项尝试移除或内联本次新增的层、抽象和状态，用第 3 步的同一组检查对比。检查仍通过、且读者负担不增，就保留简化；否则恢复。无法验证的项保留并标为 Unknown。报告每项的去留和依据。

再逐条核对：每条验收对应哪项检查、结果是什么。对不上的先补实现或检查；确实做不到的列为缺口，不改写验收去迁就实现。

完成条件：每条验收都有检查与结果，或列为缺口。

## 5. 审查

对账完成后，以本次工作开始前的提交为 fixed point，调用 Skill `code-review`，把入口清单和对账结果作为证据一并交给它。轮次和范围归 `code-review`，最多 3 轮。按严重度处理 finding：

- **P0/P1**：写出根因，修复并排查同类位置，再进下一轮。
- **P2**：先在项目 tracker 里查重，没有同类就发 issue，正文写触发场景、影响、证据坐标与修复方向。项目把这类问题归为阶段性延后加固时，按项目规则登记，不发 issue。本 Skill 授权这一步的远程写入。不在本次修复。
- **P3**：留在报告里，不处理。
- **R3 后仍有 P0/P1**：停止，不提交成功结论。用 `postmortem` 记录已确认的失败教训，用 `retro` 提出环境改动建议；把两者的结果和未解决的问题交给用户。

完成条件：两轴 verdict 都是 `PASS`，每条 P2 都有 issue 链接或登记位置；或已经按上一条停止并交给用户。

## 6. 提交

提交到当前分支。提交说明写：验证命令与结果、不写测试的理由、未跑的检查与剩余风险。

完成条件：交付说明列出每条验收的检查与结果，或列为缺口。
