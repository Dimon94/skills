# To Tickets

输入是一个 MMF 的 Spec（`to-spec` 产物）。输出是一组 ticket：合起来恰好实现 Spec，能按波次并发开发，每张大小相近。ticket 是 MMF 的 MR 分支内的工作边界；整个 MMF 做完一次审查、一次合入、一次上线。

**例外模式**：用户看过本 MMF 的票数与拆分信号合计后，确认它切不开、又要逐票合入时，完整读取 [例外模式](references/release-per-ticket.md)，它在本文件之上叠加增补。

## 词汇

- **合同票**：第 1 波唯一的票。落地 Spec Interface 代码里的签名、共享写入目标的全部变体（枚举、注册表、路由表、配置键、迁移序号）、返回“未实现”的桩和验收夹具；不实现任何 T。它让后续行为票对着冻结的签名并发开发，而不是排队改同一个文件。
- **行为票**：负责一组 T/R，交付一个可检查结果「谁 · 从哪个入口 · 做什么 · 看到什么」。
- **结构票**：只改结构、行为不变，服务紧随其后的行为票。**spike**：产出答案而非生产代码。
- **Owns / Respects**：Spec 每条 T 和 R 恰好由一张票 `Owns`；票只需遵守、不负责实现的 R 写 `Respects`，不算覆盖。R 的 owner 是实现它机制的那张票（对照 Spec 中 Module 的 `Owns:` 行）。
- **波次 / 关键路径**：依赖图的层与最长链。同一波可以并发；关键路径决定 MMF 最短交付时间。

## 切分

先判输入。输入切成两半、每半都能单独上线且单独有人用，它不止一个 MMF：停下，以 `NEXT: to-epic <理由>` 交回调用方（独立调用时请用户运行 `/to-epic`），列出 MMF 候选。只切出一张票也走完全部步骤，切片表只有一行。

1. **读 Spec。** 参数是 Issue 时读全文与评论。列出全部 T、R、User Story 编号，每个 Module 的 `Owns:`，以及 Interface 代码。按目标项目词汇读相关代码，找到每个 Interface 与共享写入目标的真实坐标。完成条件：每个编号、Module、Interface 都有坐标或标 Unknown。
2. **切合同票。** 把本 MMF 新建或改动的 Interface 签名、共享写入目标的全部变体、桩与验收夹具放进合同票。验收是：编译通过、桩可调用、夹具能跑且对未实现的行为报红。Spec 没有新建或改动 Interface、也没有共享写入目标时，不设合同票。Interface 形状或技术可行性答不上来时，先切 spike。完成条件：后续每张行为票要用的 Interface 与共享目标都在合同票里，或写明它为什么不进合同票。
3. **切行为票。** 把 T 按可检查结果分组，每组一张票；每条 R 分给实现其机制的票，其他票写 `Respects`；每条 User Story 至少落到一张票。拆法见 [拆法库](references/splitting-patterns.md)，先做强制规则和价值最大的路径。某票需要先加深一个 Module 才能把改动变小时，在它前面放结构票；被替换的是没有外部调用方的内部 Interface 时，按运行时目录完整读取 `principle-migrate-callers-then-delete-legacy-apis/SKILL.md`，迁移与删除都放进本 MMF。不设「集成」「联调」「回归」票：整体验收是 MR 的 code-review Spec 轴。需要人工签核的 R 由一张行为票负责。完成条件：每张行为票通过下方切片检查。
4. **连依赖边。** 只连两种边：依赖合同票；或本票的验收必须先有另一张票交付的行为（例如没有会话就无法验证回合）。调用 Interface 不连边，签名已在合同票冻结；同 Module、同文件不连边。同一波两张票仍要写同一个共享目标时，先把该部分前移到合同票；单一写者是真不变量时，按运行时目录完整读取 `principle-separate-before-serializing-shared-state/SKILL.md` 再决定连边或合票，并写明不变量。完成条件：每条边写明它依赖的行为或合同。
5. **定粒度。** 调用 `ticket-sizing`，取每票拆分信号与本 MMF 的票数、合计；超过拆分线的票按它的拆分步骤沿独立验收边界切开。一张行为票不负责任何 T/R，就并入相邻票。拆分信号只留在规划侧。完成条件：每票有拆分信号；没有空的行为票。
6. **核对。** 按下方票面格式写票草稿，保存到执行 agent 读不到的规划位置（目标项目仓库之外，或约定的规划产物位置且不被票引用），运行：

   ```bash
   node <本 Skill 目录>/scripts/check-tickets.js <spec.md> <tickets.md>
   ```

   `error` 全部修完再继续。`overlap` 警告逐条处理：把共享部分前移到合同票，或写明为何接受合并冲突风险。完成条件：零 `error`；`waves`、`critical-path` 输出已记录。
7. **交回裁决。** 汇总切片表、脚本输出的波次与关键路径、`ticket-sizing` 的每票拆分信号与合计，写出推荐（照此执行、重切或转例外模式）和理由，然后停下，把这些审阅材料与草稿路径交回调用方；调用方把它交给用户审阅（编排方经发布前的计划审核点，独立调用时直接展示给用户）。选重切时以 `NEXT: to-epic <理由>` 交回（独立调用时请用户运行 `/to-epic`）；选例外模式时读取例外模式补做增补。完成条件：用户在发布前看到以上全部内容并选定。

| 票 | 波次 | Kind | Owns | Respects | Stories | 可检查结果 | Blocked by（依赖的行为或合同） |
| --- | --- | --- | --- | --- | --- | --- | --- |

8. **发布并读回。** 发到目标项目配置的 tracker，按波次顺序先发被依赖的票，把草稿里的本地 id 换成 tracker id。每票设为 Spec 的子 Issue，并用原生 blocking 关系；票面的 `Blocked by:` 行同时保留（派发方从这一行读依赖）。默认打 `ready-for-agent` 标签。不关闭、不修改 Spec Issue。发布后读回每票的父子关系、阻塞关系与正文，对读回正文再跑一次第 6 步脚本。远程写操作需要用户明确授权。完成条件：读回结果与获批切片表一致，脚本零 `error`。

### 切片检查

每张行为票逐项过；任一项答不上来就重切。

1. **删除测试**：删掉这张票，会有一个人能观察到的结果跟着消失。
2. **可检查**：结果写成「谁 · 入口 · 做什么 · 看到什么」，能在分支上单独检查。
3. **一种变更**：结构变更和行为变更分开。
4. **有归属**：`Owns` 至少一条 T 或 R。

## 票面格式

草稿每票一个 `## <本地 id>: <标题>` 块；块内正文就是发布正文，只用 `###` 小节。字段只放在首个 `###` 之前；小节正文里的同名行不作字段。字段名可写成 `**Blocked by**: 02` 或 `**Blocked by:** 02`。

`Blocked by` 无依赖写 `None` 或 `无`；依赖票尚未创建时写 `Unknown（原因）`。后者产生警告，本票及下游不可派发，不计入波次与关键路径；创建依赖票后填入票 id，再运行核对。

```markdown
## 03: 用户停止正在运行的回合并保留部分结果
- Parent: <Spec Issue>
- Repo: tiktok-ad-automation
- Kind: behavior
- Owns: T9
- Respects: R11
- Stories: 12, 13
- Modules: PiTurnRunner
- Blocked by: 02

### What to build
从用户视角写本票交付的端到端行为，只写相对 Spec 的增量。

### Acceptance criteria
- [ ] T9：<一句可观察结果>（检查入口见 Spec Testing Decisions 的 T9 行）

### Prereq check
依赖上游能力时写可执行检查与期望证据；没有就删掉本节。
```

`Repo` 照抄 Spec Dependencies 节的 `Repo:`，派发方据此选择仓库。

规则：不复制 Spec 正文，不写固定样板段落，不写文件路径，不写 token 数字。原型产出的状态机、schema 或类型形状比文字更准时，可内联最关键的部分并注明来源。

## 审查现有拆票

把现有票转成票面格式，跑第 6 步脚本，再逐票过切片检查。重点信号：第 1 波只有一张实现行为的骨架票，其余全挂在它下面；R 写在多张票上而无唯一 owner；同一波多张票改同一个枚举或入口；「联调」「集成」「上线」票；票正文大段复制 Spec。每条 finding 指向票号与未过的检查项或脚本规则。已派发或已被 claim 的票只提建议，不改写。
